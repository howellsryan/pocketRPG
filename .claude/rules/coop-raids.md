# Co-op Boss Fights & Raid Parties (`/api/coop/**`)

Path-scoped rule — auto-loads when working on co-op or raid code. See `CLAUDE.md`
§20/§21 for the pointer. Bare `§N` below means `CLAUDE.md §N`.

## Co-op Boss Fights (`/api/coop/**`)

Several players versus one shared boss, in the idle game. **Allowlisted per boss** (`COOP_BOSSES` in `src/engine/coopBossEngine.js`): every boss in `monsters.json` **except raid bosses** (which are group-playable only inside a raid party, see Raid Parties below) and the solo-only four — the Ember Pits pair `ember_tyrant`/`ashen_crucible`, plus `venomcoil_matriarch` and `blighted_gauntlet`. Keep it an explicit list, not a filter over the monster data, so opening a boss to groups stays a deliberate edit. The wait between kills is **flat: `COOP_RESPAWN_TICKS` = 8 ticks / 5s for every boss** (8 because the HUD renders `ceil(ticks * 0.6)`, so 8 is the longest wait still reading "5s") — a deliberate replacement for the old per-boss `clamp(round(12750 / hitpoints), 10, 100)` curve, which paced the farm loop off the boss's HP (Grondar 255 HP → 30s; the Horror 2000 HP → 6s). One predictable number beats a curve players cannot see, but it does mean a squishy boss's GP/XP per hour is no longer held back by its respawn: pace a new co-op boss with its drop table or its HP, **not** by reintroducing a per-boss delay.
- **Picking solo vs group**: tapping an allowlisted boss in the combat picker opens a choice prompt (`coopChoice` in `CombatScreen.jsx`) — solo runs the normal client-side fight, group joins a server session. Any other entry point into `startFight` (auto-start, slayer, dungeon) stays solo.
- **The group fight must look like the solo fight.** `CoopBossScreen` renders the same mobile HUD as `CombatScreen` — back link, fight header, HP blocks, prayer bar, `CombatQuickActions`, `cb-actions` row — and the shared blocks live in `src/components/CombatHud.jsx` so the two cannot drift. Add HUD markup there, not to one screen. A boss kill announces itself to each loot winner the same way solo does (§6): a purple/gold reward-reveal card (`emitKillReveal`), so the group fight carries on same as the respawn wait's live countdown; only a **raid completion** still stops the room on the full-screen `LootResultModal` (shaping shared via `src/utils/lootModal.js`). Two deliberate co-op-only surfaces exist. First, the **loot share bar** (`src/components/CoopLootShare.jsx`, `.cb-loot-*`), a hairline track under the boss's name in `CombatFightHead`'s `meta` slot: it exists because the 10% threshold made "am I getting a drop" a decision the player has to make mid-fight. It measures the player's OWN damage against the *threshold*, not the boss's health — so it fills across the 0–10% they need and turns solid verdigris at "drop secured". It started as a full roster panel of every member and that was **too tall for a phone**; keep this a glance, not a scoreboard. Deliberately absent: any per-member damage table, and any Leave button beyond the standard back link. Second, **fight chat** (`src/components/CoopChatPanel.jsx`, `.cb-chat-*`) — same 44px band open or shut, because shut it is the newest line and a purple-drop announcement has to land in front of a player who never opens the log. **The respawn wait is prep time**: `processCoopTick` applies intents *before* the respawn early-return, so the group can eat, drink and swap gear between kills — and because no combat resolves during the wait, `tickIdleCooldowns` walks the consumable cooldowns down by hand (without it one bite blocks the rest of the wait). Server-side gaps show as parity gaps, so every quick-action needs its intent: `equip` enforces level/quest gates against the `levels`/`completedQuests` the member carries from join (fails **closed** — a session predating those fields equips nothing gated) and refuses rather than drops gear when a 2H swap won't fit the pack.
- **The fight runs in a Durable Object**, not on D1. `CoopBossRoom` (`world/server/CoopBossRoom.ts`) holds the state in memory and advances it on its own 600ms `setInterval`; `/api/coop/session/[id]/{tick,intent,leave}` are authenticated thin proxies (`functions/_lib/game/coopRoom.js`). D1 is written on join, leave, kill settlement and a 25-tick checkpoint — **never on an ordinary tick**. Migrations 0031 + 0032. The class is a **local export of the one Worker**, bound as `COOP_ROOM` (`wrangler.jsonc`). It used to live in a second Worker and be bound cross-script, because a Pages project cannot export a DO class — that is where the two-deploy rule, the `coopRoomsAvailable`/`COOP_UNAVAILABLE` degradation and the raid capability probe all came from, and all three are gone. **Don't reintroduce a split**: `CoopBossRoom` is called only from `/api/coop/*`, so hosting it elsewhere puts a network hop between a route and the object it drives, and lets the two versions disagree. **A tick is published only once nothing more can be appended to it** (`publishedTick`, advanced in `tickInner`'s `finally`; `eventsSince`'s `untilTick`). Events are keyed by tick and a client acknowledges the tick it was told about, so anything appended *after* that — settlement runs several D1 round-trips **per winner** and appends `killSettled` to the tick `bossDefeated` already went out on — is filtered by `> since` forever. That is the bug that ate the loot modal in group fights; never publish a tick mid-settlement. A `poll` returns the state plus every event after the caller's `sinceTick`, projected for that caller (`projectEventsForMember` strips the other winners' drop lists off a `killSettled`, as `projectStateForMember` strips their packs) — don't go back to per-request events, that is what left members seeing ~1 tick in 8.
- **Kill settlement is exactly-once and runs after the tick commits.** `coop_kill_settlements(session_id, kill_seq)` is the idempotency key and it lives in D1, not the room: a DO can be evicted mid-grant and replay. Never settle before the state it settles is durable, and seed `killSeq` from the ledger on reload, not from the session row.
- **A prayer's slot comes from its data, never from the caller.** `toggle_prayer` routes through `coopPrayerSlot` (`bonusType === 'protection'` → `activeProtectionPrayer`), because combat.js only mitigates from that field: taking the slot off the intent filed every protect-from-X as an offensive prayer, so it blocked nothing *and* cancelled the offensive prayer — flicking a boss in a group could not work at all.
- **The room PUSHES the beat over a WebSocket; polling is the fallback, not the plan.** `src/cloud/coopFeed.js` owns the connection and `CoopBossScreen` only receives beats — it must not learn which transport carried one. Polling cost a Worker invocation, a JWT verify and a `getOwnedCharacter` **D1 read per member per 600ms** (~800 reads/min for a full room) to deliver a fight that was always a round trip stale; the socket costs one D1 read per *connection*. A browser cannot put a header on a handshake, so `POST /api/coop/session/:id/socket` mints a **60s `coop_socket` ticket** (bound to character AND session) and the `GET` on the same path verifies it *at the edge* before proxying the upgrade to the room — an unauthenticated socket must never reach a DO. Frames are **deltas** against the projection each socket was last sent (`src/engine/coopSocketProtocol.js`, per SOCKET not per member — a reconnect can double up), and a beat where only the tick counter moved with no events is **not sent at all**, which is what makes sitting in a raid lobby free. Two rules carry over unchanged: a tick is pushed only from `tickInner`'s `finally` (never mid-settlement, the `publishedTick` rule above), and `validateCoopAction` now lives in `functions/_lib/game/coopIntent.js` because a socket frame **never passes the edge** — leaving it there let chat through unsanitised and `toggle_prayer` through without its data-derived slot. The fallback survives on purpose — a network that blocks WebSockets answers non-101 → the client polls, paced by `nextPollDelayMs`/`src/utils/coopPolling.js` against the room's `next_tick_in_ms` (a flat 600ms wait drifts a round trip out of phase and arrives in clumps). A tap is still echoed locally until the room answers (`coopIntentEcho` — the toggles only, mirroring `applyCoopIntent`; the screen drops the echo at the tick the intent was stamped for, so a refusal simply un-does it).
- **A closed socket is weak evidence of absence, and being let go is never a dead end.** Losing the last socket back-dates that member's `lastSeen` by `COOP_SOCKET_LINGER_MS` so the ordinary staleness path ejects and writes them back — back-dating rather than a second timer, so any later poll or reconnect undoes it for free. The constant is **45s and must not be shortened back**: it was 10s, tuned only for the player who has GONE (the save lock follows the member, below), and a phone closes sockets for a locked screen, an app switch or a wifi handover — a *suspended tab runs no timers*, so it cannot reconnect until the player looks at it. At 10s a glance at a notification cost the fight. Because a member can always be let go, the client treats `not_a_member`/`ejected`/`session_ended` as **rejoinable, not fatal** (`isRejoinableCoopCloseReason` → `coopFeed`'s `onLost` → `rejoinCoopFight`): pull the save the room wrote on the way out, then rejoin — the **same party** for a raid (joining one without a `sessionId` opens a NEW party, see Raid Parties below, stranding the returner alone in a lobby), any room for a boss. A boss rejoin usually returns the SAME `sessionId`, so `CombatScreen` remounts the screen off an attempt counter, never off the id. Checkpoint cadence: **15s in a fight, 60s in a lobby** (nothing is at risk in a lobby; membership/phase/readiness still force one immediately), heartbeat rows refreshed per member every **30s** against a 90s lock TTL, and both folded into **one `DB.batch`**. Do **not** lengthen the 15s fight checkpoint to save rows — its cost is a player's lost progress when a DO is evicted mid-fight.
- **The heartbeat row is a MIRROR of the room's `lastSeen`, and what is tracked is the VALUE it holds — never when it was last written.** `/api/save` decides the save is locked by reading `coop_session_members.last_seen_at` against a 90s TTL, so the only question worth asking of that row is how close its value is to expiring; `heartbeatValue` answers it, a write timestamp cannot. Tracking the write time let a save escape the lock **mid-fight**: a closing socket back-dates `lastSeen` by `COOP_SOCKET_LINGER_MS`, and every checkpoint that followed re-wrote that same stale value and re-armed a fresh 30s block, so a member who reconnected inside the linger stayed in the fight while their row kept a value that expires 45s after the close. The idle client's next push landed, the room's copy of their `saveRevision` was orphaned, and every kill after it was refused as diverged — a player with 561 damage on a 150 threshold was paid nothing. Two rules follow. (1) **Proof of life that cannot wait for a checkpoint writes through immediately** (`touchHeartbeat`, on socket accept / poll / rejoin) — a checkpoint is 15s away in a fight and 60s in a lobby, both longer than the margin a back-dated row has left; it is gated on the row already being stale, so a beat still costs no D1, and the write is not awaited by a socket upgrade. (2) **A member whose write-back was refused as diverged is RELEASED, not fought on** (`pendingDivergedRelease` → `releaseMembers`): nothing they do can reach their save again, so every later kill settles to nothing. The release is drained a beat LATE, because `broadcast` closes the socket of anyone missing from `members` and would swallow the `killSettled` event that explains it; `ejected` is a reason the client rejoins from, so the player pulls the save the room just wrote and comes back on a snapshot that owns it.
- **While a room owns the character the client neither SIMULATES nor WRITES.** `CombatScreen` holds `suspendSaves()` for the life of the session, so the push loop is already off — but three things ran anyway, and each one is a way to lose the fight. (1) The **background activity runner** kept a skilling task going (`isRunnableBackgroundTask`'s `coopSessionActive`, an option rather than a fourth untested guard in `App.jsx`): the room is spending from the same pack, and the pull on the way out throws the products away, so those herbs are consumed for nothing. (2) The **visibility-return catch-up** simulated the window the room had just been paid for, and — worse — its `checkCloudNewer`/`applyCloudSave` adopted the room's mid-fight revision, which is how the client came to hold one the write-back no longer matched; it now consumes the `hiddenAt` stamp and returns (consuming it is required, or the next return simulates the fight again). (3) **`beaconSaveNow` was the one save writer that ignored the hold.** That is the worst possible leak: it fires on the very event that ends a co-op socket (a phone locking, a tab going away), carries the client's pre-fight blob with `interactive: true` so the idle ceiling cannot stop it, and its outcome is unreadable, so it bumped `lastSaveRevision` and settled the loss ledger and kill tally as though the server had taken it — whether or not the lock refused it. It gates on a refcounted `holdServerOwnedSave()` (taken beside `suspendSaves()` for the session, released with it — the server's lock outlives the client's until the leave lands), deliberately **not** the `savesSuspended` refcount: a short client-owned holder raises that too (the paid skip's `lockGame`), and it holds the only copy of an hour a credit has already been charged for, so its teardown flush is the one that must still go. Anything new that writes the save or advances the game on a timer needs the same gate. The marker is in-memory, so a tab RELOADED mid-fight is still ungated (as is `gameState.jsx`'s boot catch-up) — bounded to refused pushes by the server lock above, and closing it properly needs a durable marker like `worldHandoff.js`'s.
- **Client settings edited mid-fight ride the member, not `/api/save`.** The co-op lock refuses this character's own save push and `sync.js` *drops* it, and the client pulls on exit — so anything the player changes during a fight is lost unless the room carries it. `quickPrayers` works this way (seeded in `createCoopMember`, edited by the `set_quick_prayers` intent, written back by `applyQuickPrayersToSave`); an absent field means a pre-feature session and must leave the save's value alone rather than writing an empty one. Any future in-fight setting needs the same three pieces.
- **Nothing may write the save while a room owns it.** The member's save revision is stamped at join and re-checked on every write-back (`isMemberSaveOwned`); a mismatch **refuses the write entirely** — replaying the snapshot duplicates items, writing XP alone refunds the supplies. Prevention is `assertNotInCoopSession`, which every save-writing endpoint calls (`/api/save`, `purchase`, `trading-post/**`, `actions/**`, `skip-hour`, world entry). Add it to any new one.
- **Combat mirrors the open world** (`world/server/combat.ts`): each member runs their own `processCombatTick` session against the shared boss HP, so authored boss mechanics keep working. Two invariants — only the **target** member's session resolves a boss swing (otherwise the boss attacks once per member), and only the target advances the **add's** spawn countdown (otherwise N members each spawn one).
- **Loot goes to everyone who earned it**, not one winner: every member whose own damage reached **10% of the boss's max HP** (`killCreditIds` via `lootEligibleCharacterIds`; ceil, so the floor is 1 and a 0-damage member never qualifies) rolls the drop table **independently** and is granted server-side with the same collection-log/kill-count/audit side-effects as `/api/actions/monster/complete`. Attribution is the boss's HP delta across a member's tick, so every damage source counts; damage resets per boss instance on respawn, and the gate is damage-only (a member who qualified and then died is still paid — which is why slayer and kill counts, now on the same gate, dropped their alive checks). The cap of 8 means the top contributor always clears 12.5%, so a kill can never come out dry for everybody. Idempotency is therefore per CHARACTER — `coop_kill_settlements` is keyed `(session_id, kill_seq, character_id)` (migration 0032) — and the per-member settlements are independent, so one diverged save never costs the other winners their drop. A skip cannot be used to jump the threshold: `/api/skip-hour` refuses while a room owns the character.
- **Chat and purple-drop announcements are instance-wide broadcasts, and both ride the room's event ring.** Chat arrives as a `chat` intent (sanitised at the edge *and* in the room by `sanitizeChat`, `src/engine/playerChat.js`), takes **no** combat action slot and works while dead or mid-respawn, and is rate-capped per member (`chatRateVerdict`). It is queued in `pendingChat` and published on the **next** tick, never appended to the current one — an event added to a tick a client already acknowledged is filtered by `> since` forever, the same rule that keeps settlement off its own tick. Every message writes an audit row (`coop_chat`; the world writes `world_chat`) with `swallow: true` — a safety history, and an audit outage must not silence the room. The **purple-drop** announcement (`epicDrop`, `coopEpicDropEvents` in `src/engine/lootBroadcast.js`) fires for every winner whose grant contains an item past the loot modal's purple threshold (`isLegendaryItem`, unit value ≥ 1m — keep the two predicates the same, or the room celebrates something the winner does not). It carries that item only and is deliberately **not** stripped by `projectEventsForMember`: who pulled a legendary is public, the rest of their drops are not. The open world runs the same announcement through `dropBroadcastsFrom` (`world/server/bossKills.ts`), where it is **not** a boss privilege — value is the reason to shout — and a boss unique that is also legendary announces once, as epic.
- **Instances are sharded**, capped at `COOP_MAX_MEMBERS` (8): joining picks the fullest non-full session, else opens a new one — never one global boss per boss id.
- **The save lock follows the MEMBER, not the room** (`coop_session_members.last_seen_at`, 90s TTL; `characters.active_coop_session_id`; same lock class as the world session). A room stays alive while anyone is in it, so a session-wide clock left a crashed player locked out of their own save for as long as the others kept fighting. The room ejects its own stale members and **writes them back before releasing** — as does the crash sweep, so a dropped connection costs the fight, never the XP. The client must pull the save on exit, never push its own — so a push refused by the co-op lock **drops** its snapshot (`sync.js`) instead of queuing it the way the world lock's push does, or the pre-fight state lands on top of the room's write-back the moment the lock lifts. Joining WRITES the save (the snapshot), so `/api/coop/join` returns `save_revision` (on its error path too) and `cloud/coop.js` re-anchors from it; the pre-join flush treats `CHARACTER_IN_COOP_SESSION` as "a room already owns me", not a failed save, and joins anyway — refusing wedges the player behind the one call that releases the lock.
- **Boss entry gates are enforced server-side** (`coopBossRequirementFailure` → `checkBossRequirementsPure`): Slayer level and kill-count prerequisites, not just the quest. The server grants this boss's drop table, so a client-only gate is no gate.

## Raid Parties (`/api/coop/raid/**`)

A raid run as a co-op session (the section above is the substrate — same room, same tick, same save lock, same 10% loot gate). Only what differs from a boss room is below.
- **A raid has a lobby; a boss room does not.** `phase` on the session state is `'lobby' | 'active'`; members may be added **only in lobby** and the gate is enforced in the ROOM (`CoopBossRoom.handleJoin`), not just the join path — the D1 row is a checkpoint behind, so it cannot be the authority on whether the host has set off. `phase` changes force an immediate checkpoint, or the lobby list keeps offering a run for seconds after nobody can enter it.
- **The host starts it.** `hostCharacterId` (the opener); `start_raid` is an ordinary intent so it orders with the tick loop — no extra endpoint. `removeCoopMember` promotes the earliest-joined member when the host leaves (`nextHostCharacterId`), or a party is stranded with a Start button nobody can press. The lobby is prep time exactly as the respawn wait is: intents apply, `tickIdleCooldowns` walks cooldowns down, nothing fights.
- **No auto-pick.** `POST /api/coop/raid/join` with no `sessionId` means **open a party**; with one it means **join that party**. Deliberately unlike the boss join, which picks the fullest room — which party you raid with is the player's call, so a full/started party is an honest refusal (`RAID_ALREADY_STARTED`, `COOP_SESSION_UNAVAILABLE`), never a reroute.
- **A raid pays once, at the end, from its own table.** Intermediate bosses emit `raidBossDefeated` and return **no kill record** — mirroring solo (`combat.js` rolls loot on `raidComplete` only). The final boss's kill record carries `sourceType: 'raids'`, and `killRewardSource` routes settlement to `rollRaidRewardsById` with collection-log and `kill_counts` filed under `raids`/`raidId`. Slayer credit lands on the final boss only, mirroring solo's `fromRaidCompletion` gate.
- **The loot gate measures the WHOLE run.** `coopLootBasisHP` returns `raid.maxHP` (every boss's HP summed at raid creation, `raidTotalHitpoints`) and member damage is **never reset between bosses** — reset it and a member who carried five bosses goes dry on the sixth. The sum counts **health the party actually removes, not health bars**: a phased boss adds every phase (Verzik 2000+3250+2500) and a `requiresDoubleKill` boss counts twice (Olm 800×2). That second bar only exists because `doubleKillCount` lives on the **shared boss record** (`state.boss`), not the member — member combat sessions are rebuilt from scratch each tick, so a per-member count regenerates the boss forever and the raid can never be finished.
- **Finishing or wiping returns the party to its lobby** (`returnPartyToLobby`) so the host can start again without regrouping; eligibility is read before the reset clears the damage it is measured from. That happens on the **same tick** the settlement publishes `killSettled`, so `CoopBossScreen` builds its loot modal **before** the lobby early-return and renders it from both branches — a modal rendered only by the fight view is set into state and never seen, which is exactly how a cleared raid paid out silently. **Dead members are not revived** — death must cost what it costs solo, and reviving also hides the death from the client, which is what reverts one-life mode.
- **The party sets off together: readiness GATES the start.** `set_ready` (lobby-only, silent outside one) sets `member.ready`, projected by `lobbyMember`; `raidPartyReady` is the gate and `raidReadyCount` the same count the lobby shows — enforced on the `start_raid` intent (`party_not_ready` refusal), not by disabling the button, which is not the authority. Both read one roster (`readinessRoster`) that excludes the **host** (Start is their answer) and the **dead** (a party returns from a wipe with its casualties, they are never revived, and the intent path refuses actions from a dead member — counting them strands the party behind someone who cannot answer). Cleared by `startCoopRaid` and `returnPartyToLobby`. New intent → add its case to `validateCoopAction` (`functions/api/coop/session/[id]/intent.js`) too: that allowlist runs at the edge, and a missing case is a 400 `unknown_action` the room never sees.
- **The lobby is the one place a member's kit is public.** `projectStateForMember` swaps `publicMember` for `lobbyMember` (adds equipment/inventory/levels) **only while `phase === 'lobby'`** — sizing up the party is the point of the screen, but eight full packs per 600ms beat is payload nobody reads. `CoopRaidLobby`/`CoopRaidPartyList` are the surfaces; the fight itself is `CoopBossScreen` unchanged, with a `Boss n/N` counter.
- Migration **0034** (`raid_id`, `phase`, `host_character_id`). `boss_id` holds the raid's CURRENT boss so every boss-room query above still works; boss-browser queries filter `raid_id IS NULL` so a party can never surface as a boss room.
