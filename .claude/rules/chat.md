# Help Chatbot (`/api/chat`)

Path-scoped rule — auto-loads when working on chat code. See `CLAUDE.md` §16 for the pointer.

- In-game helper (floating 💬, `src/components/ChatWidget.jsx`) that both answers PocketRPG questions **and performs actions** on the player's account. Backend `functions/api/chat.js`: tries `CHAT_OPENAI_MODEL` first (OpenAI chat completions + `OPENAI_API_KEY` secret, skipped entirely if unset; called with a pinned `CHAT_OPENAI_REASONING_EFFORT` rather than the API default, since its tool calls include real writes), then `CHAT_MODEL` in `functions/_lib/chat/prompt.js` (`@`-prefixed = Workers AI `env.AI`; otherwise Gemini via Google's OpenAI-compatible endpoint + `GEMINI_API_KEY` secret) when OpenAI is unconfigured or fails/answers empty, then `CHAT_FALLBACK_MODEL` on Workers AI when both fail/answer empty (`chatAttempts` in `chat.js`) + lexical retrieval over a generated knowledge index + the MCP tool surface via `callTool` (allowlist = all `TOOL_NAMES`; `character_id` pinned server-side). No web access. **Tool exposure is progressive, not the full ~50-tool surface every call**: each request only declares `ALWAYS_ON_TOOL_NAMES` (the reads nearly every turn needs) plus a `search_tools` meta tool; a `search_tools` call ranks `TOOL_SCHEMAS` by query and reveals the matches for later rounds in that same request to call (`runAiChat` in `chat.js`; `searchToolsByQuery` in `prompt.js`) — keeps the per-call schema payload small and the tool choice unambiguous for the primary model. Raising `CHAT_MAX_TOOL_ROUNDS` needs a matching raise of `CHAT_MESSAGE_RESERVE_MILLI`/`CHAT_OPENAI_MESSAGE_RESERVE_TOKENS` in `quota.js` (see its comment) — check the free-tier neuron headroom first.
- **Write gating (`functions/_lib/chat/actions.js`)**: reads run inline; the first **write** tool the model calls (annotation `readOnlyHint:false`) is *never executed inline* — it's captured, HMAC-signed into a short-lived token (reuses `JWT_SECRET`), and returned as a `pendingAction` the widget renders as a Confirm/Cancel card. Phase 2 (`{confirm:token}` body) verifies the token (signature/expiry/character), **charges the 1-credit action fee first** (`CHAT_ACTION_FEE`, atomic debit on `characters.credits` — before any execution or AI spend; refunded if the action errors), then executes via `callTool` and phrases the result. Confirm card shows the total credit cost incl. any skip (`actionCreditCost` = fee + `kill_boss`/`kill_raid`/`skip_hour`/`skip_slayer_task` skip credits). One fee per confirmed action regardless of how many updates it makes.
- Models (`chatAttempts`): **OpenAI (`CHAT_OPENAI_MODEL`) is the primary**; the **free Workers-AI `CHAT_FALLBACK_MODEL` is the first failover**; **paid Gemini (`CHAT_MODEL`) is the last resort** — each reached only when the earlier ones are unconfigured/fail/answer empty/run out of budget. A Gemini 429/503 retries with short backoff, then falls through.
- Cost guards: **30 messages/char/day** (`CHAT_DAILY_LIMIT`; `claimCharacterMessage`, refunded on a retrieval-only degrade); when spent, the widget offers a **paid refill for 10 credits** (`CHAT_REFILL_CREDITS`, `{refill:true}` body → atomic credit debit + `resetCharacterMessages`). Plus three global daily spend budgets (reserve-then-settle; `functions/_lib/chat/quota.js`, migration 0027): OpenAI meters its own token pool (`openai:` day_key, 2.2M/day free data-sharing allotment — metered since overage bills), the free Workers-AI failover meters the neuron budget (≤10k free neurons/day), and paid Gemini meters its own token pool (`gemini:` day_key, a pure $ cap). An exhausted pool skips only its own attempts. Any AI-path failure — budget exhausted, missing key, model error, time budget hit (`CHAT_TIME_BUDGET_MS` 90s, under the client's 110s fetch timeout in `src/cloud/api.js` — keep that margin or the client aborts to a "too much for me" error instead of taking the retrieval answer), empty answer — → retrieval-only answer, never a bare apology. **An empty answer is a silent quality failure, not just a fallback**: the OpenAI attempt reports one when `max_output_tokens` runs out, and on a reasoning model that budget funds thinking as well as the reply, so `CHAT_OPENAI_MAX_OUTPUT_TOKENS` is separate from (and much larger than) the shared `CHAT_MAX_ANSWER_TOKENS` — starve it and every turn quietly drops to the GLM failover. It is also why the OpenAI worst-case reserve in `quota.js` dwarfs the other pools'. Tool calls run in parallel; a failing tool degrades to a `Tool error:` message the model can route around.
- **Jev tool-routing POC is optional and off by default.** `CHAT_JEV_TOOL_ROUTING=true` routes only the model's short `search_tools` phrase plus static tool descriptions through TypeSafe Jev; `TYPESAFE_API_KEY` stays server-side. Never send character/account state, auth, bank/inventory contents, action arguments, saves or tool results to Jev. Missing key/API failure falls back to the existing lexical router; an explicit Jev no-match does not, so benchmarks expose real misses. Evaluate with `npm run benchmark:chat-routing` before any rollout.
- **Arithmetic about the player's account is never the model's to do**, and both tools that replace it are in `ALWAYS_ON_TOOL_NAMES` for the same reason: behind `search_tools` a model skips them and answers confidently from raw data instead, which is wrong every time. `analyze_dps` (§15, `functions/_lib/mcp/dps.js`) owns "best setup", "melee or magic here", "is this an upgrade", "how do I kill X faster". `plan_training` (`src/engine/trainingPlanner.js`) owns "how many bones to 77", "how long to 99", "what will that cost" — asked one of those, a model picked the wrong training option, assumed a gilded altar the player had no house for, and ignored that a Grindman needs double. Its schema is kept deliberately small so the always-on cost stays near zero.
- **`get_character_state` carries the account modes** (`isIronman`/`isOneLife`/`isGrindman`, from `resolveCharacterRow`). Without them the model cannot get any XP rate, time-to-goal or drop-rate answer right for a Grindman, and has no way to know it is wrong.
- Both computing tools keep their default payload small — `analyze_dps` is opt-in wide (`include: ['upgrades','levels']`), the planner reports segments rather than per-level detail — so the answer stays under `CHAT_MAX_TOOL_RESULT_CHARS`; a payload truncated mid-JSON is one the model reads wrong. Adding a tool schema grows the worst-case reserve `tests/chatQuota.test.ts` derives from `chatToolDefs()` (the FULL allowlist, not the always-on set), so every new tool costs a reserve bump: `CHAT_MESSAGE_RESERVE_MILLI` trades against `CHAT_NEURON_BUDGET_MILLI` under a fixed 10M ceiling, and `CHAT_OPENAI_MESSAGE_RESERVE_TOKENS` against `CHAT_OPENAI_TOKEN_BUDGET` under 2.5M — raise the reserve and lower the budget to match, the test pins both ceilings.
- Retrieval ranking (`retrieval.js`) is BM25 plus two guards, and the second exists because term rarity lies. Title and tags are **one deduplicated field** — counting a term in both scored templated boilerplate 6 against a body term's 1. **Focus** then scales a chunk by the share of its OWN headline terms the query asked about, which is the only signal separating a chunk on the topic from one sharing a generic word: the 17 `Skill training options: X` chunks made `train` rarer (df 22) than `slayer` (df 80), so plain BM25 buried the Slayer guide at rank 19 behind every wrong skill and the helper answered that Slayer isn't in the game. Coverage cannot fix that — it scores "matched train, not slayer" and "matched slayer, not train" identically. Retune `FOCUS_WEIGHT` against `tests/chatRetrieval.test.ts`, not one query.
- Knowledge index: `npm run gen:knowledge` regenerates `functions/_lib/chat/knowledge.js` from `docs/game-guide.md` (player-facing; each `##` = one chunk) + `src/data/*.json`. Update guide + regenerate + commit when mechanics/content change. Keep the guide tight (`ruthless-editor` skill) — its chunks are retrieval context on every player chat call.
