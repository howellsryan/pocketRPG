# Tripo AI MCP bridge (`/api/tripo-mcp`)

Path-scoped rule — auto-loads when working on the Tripo bridge or its tests. See `CLAUDE.md` §15 for the pointer to the (unrelated) player-facing MCP server.

- **Not the game's MCP server.** `functions/api/mcp.js` (§15, `.claude/rules/mcp.md`) is player-facing, OAuth 2.1-gated, and forwards a player's own session token to real `/api/*` handlers. `functions/api/tripo-mcp.js` is a separate, unrelated stateless JSON-RPC server: a developer/content-pipeline tool that proxies Tripo AI's task API (`api.tripo3d.ai`) so an AI coding assistant can generate 3D models / concept art for the game without needing its own network egress to Tripo. It exists because Tripo's host is unreachable from network-restricted coding sandboxes; this Cloudflare Worker holds the Tripo key and has full egress.
- **Auth**: a single static bearer secret (`TRIPO_MCP_TOKEN`, `functions/_lib/tripo/auth.js`), compared via a SHA-256 constant-time check — not OAuth, not the session JWT. Never wire player identity or `requireAuth` into this file.
- **Tools** (`functions/_lib/tripo/schema.js` + `tools.js`): `create_task` / `get_task` mirror Tripo's submit-then-poll task API (see `scripts/tripo-worldmap.mjs`, the original local-only version of this workflow, for the same shape run by a human with `TRIPO_API_KEY` in their own env). `store_asset` downloads a URL from a finished task's output server-side and persists it to the `TRIPO_ASSETS` R2 bucket, returning a stable `/api/tripo-assets/<key>` URL (public — these are generated art/model files, not player data; keys default to random UUIDs, or pass `key` for a deliberate path like `models/<item>.v1.glb`). `get_asset` returns a stored asset's bytes as base64 (capped ~15 MiB per call; pass `offset`/`length` to chunk larger files). `upload_asset` is the write direction: base64 bytes → R2 under a chosen key (≤25 MiB decoded), so locally-processed GLBs get hosted without wrangler. The serving route is the catch-all `functions/api/tripo-assets/[[key]].js` (nested keys, immutable cache — never reuse a key, bump `vN`).
- **Adding a tool**: same three-file shape as the game's MCP (`schema.js` metadata, `tools.js` dispatch, a test in `tests/tripoMcp.test.ts`) — `tools.js` throws at import time if a schema name has no dispatch handler, so schema/dispatch can't drift silently.
- **Secrets**: `TRIPO_API_KEY` (Tripo platform key) and `TRIPO_MCP_TOKEN` (bearer secret for this endpoint) are separate Cloudflare secrets from everything the player-facing app uses — see `wrangler.toml`'s secret comments. Never commit either.
- **Equipment/monster 3D models are hosted from R2, not the repo**: processed GLBs live at `models/<id>.vN.glb` and `src/data/equipmentModels.json` references `/api/tripo-assets/<key>` (site-relative, so each deployment serves its own environment's bucket — preview and production buckets are separate; a model uploaded via preview must be re-uploaded against production before the entry works there). The first batch (scimitars, King Black Dragon) predates stable keys and sits at UUID keys — same serving path, equally immutable. `public/3d-samples/` remains for the hero + legacy samples.
- **Manual import is the primary workflow** (`scripts/import-model.mjs`, `npm run import:model -- --file <path.glb> (--item <id> | --monster <id>)`): the operator authors/exports a .glb themselves (Tripo's paid generation API is unused — `create_task`/`get_task` remain wired but idle), and one command does process → canonical grip bake (items) → optional colour variants → `upload_asset` to `models/<id>.vN.glb` (cache-busted version probe) → registry. `--variants` derives every entry in `scripts/model-variants.json` whose `base` is this item via `scripts/recolor-model.mjs` (selective hue-band remap of the base-colour texture — one authored model becomes the whole metal tier; target hues from `src/data/bespokeIcons.json`; re-imports preserve per-variant tuning; untouched textures keep their original bytes). `--monster` registers under `monsters` (`{ model, height, rotationDeg? }` — height defaults from combat level, facing is data with the default facing the hero), which auto-enables the 3D combat arena. Item textures default 512px, monsters 1024px. Needs open egress to the deployment (`--base-url`, default preview; `TRIPO_MCP_TOKEN` env for auth) — a network-restricted coding session instead drives the same steps through the MCP tools (`upload_asset` with the processed file's base64, or `store_asset` fetching a URL the worker can reach), running the processing scripts locally.
- **Canonical grip space kills per-weapon tuning** (`scripts/canonicalize-weapon.mjs`, automatic for `--item` imports): the weapon GLB is baked so its grip sits at the origin, blade along +Y, length 1 — the single `defaults.weapon` transform in `equipmentModels.json` then places EVERY weapon, and a canonical entry is just `{ "model": … }`. The heuristic (bbox longest axis = blade; thinner cross-section end = grip) is correctable with `--flip` / `--grip <frac>`; `--no-canonical` opts out (then hand-tune). Registry bone semantics (mirrored by `equipModels.js` and the aligner): absent `bone` → `defaults.handBone`; explicit `null` → model root — never conflate them.
- **Monster animation convention**: a rigged monster GLB's clips drive the arena by NAME — `Idle` loops, `Attack` plays per hit (clip-less monsters keep the procedural bob/lunge). Rename generator junk at import with `--clip <old>=Idle` etc. (`process-3d-model.mjs` applies renames and skips `flatten`/`join` on animated models so node-targeted channels survive).
- **The aligner is registry-first** (`public/3d-preview.html`): it fetches `/src/data/equipmentModels.json` (served in dev and on deployments), lists registered weapons, loads hero + weapon from the registry's own paths (R2 URLs resolve on a deployed preview) with runtime-identical bone/default semantics, and emits the paste-ready entry (collapsing to `{ model }` when it matches `defaults.weapon`).
- **Promoting to production** (`npm run promote:assets`): registry model URLs are site-relative, so preview-imported assets do NOT exist in production. After merging 3D work to main run `scripts/promote-assets.mjs` (downloads each referenced key from `--from`, `upload_asset`s to `--to` under the same key, skips existing; `--dry-run` previews). Requires the target's deployed bridge + its `TRIPO_MCP_TOKEN`.
- 2D art still lands the same way as before this bridge existed: pick the best `rendered_image` output, save it under `public/world/` (or wherever the asset belongs), and wire it into `src/data/*.json` (e.g. `world.json`'s `mapImage`) — or keep it in R2 under a stable `images/...` key and reference the `/api/tripo-assets/` URL.
