# Single-file Build Safety & 3D Asset Pipeline

Path-scoped rule — auto-loads when touching `build_single.cjs` or the 3D/GLB
asset pipeline. See `CLAUDE.md` §12 for the pointer.

- `index.html` is generated by `build_single.cjs` and gitignored (`/index.html`, `/game-*.js`) — never edit/commit it; change `src/**`. `npm run build:site` rebuilds it, builds the world client and stages both into `dist_site/` (also gitignored) for the Worker's `assets` binding.
- Top-level declarations must be **globally unique** across both output files; duplicate-identifier errors are release-blocking. Prefer `src/utils/helpers.js`.
- **No eval-time cross-module reads**: the scripts run top-to-bottom in `sourceFiles` order, so a module's **top-level** `const`/`let` initializer must not read a binding another module exports (e.g. `const IDS = new Set(SLAYER_UNLOCKS.map(...))`) — if that module is concatenated first, the import is in its temporal dead zone → `Cannot access X before initialization`, which aborts the whole inline script and whites out prod. `node --check` can't see it; `check:single` now executes the bundle to catch it. Fix by deferring the read into a function (lazy init), never by reordering `sourceFiles`.
- **Code-split**: two CLASSIC scripts (not modules) — inline core in `index.html` + content-hashed `game-<hash>.js` (heavy in-game screens, `GAME_CHUNK_FILES`), loaded lazily on `cloudPhase === 'ready'` via `globalThis.__loadGameChunk`. Classic scripts share one global lexical env; cross-refs resolve by source name. Both minify with `minifyIdentifiers: false` — **do not re-enable**.
- New in-game screen → add to `sourceFiles` **and** `GAME_CHUNK_FILES`. Landing/auth-reachable screens stay **out** of `GAME_CHUNK_FILES`; core must not reference a chunk binding at module-eval time (only inside `renderScreen`).
- `gameIconsData` (~126 KiB) and `worldActivitiesData` (~150 KiB, `src/data/worldActivities.json`) are in the chunk. Core code guards every access (`typeof gameIconsData !== 'undefined'` + emoji fallback in icon code; `placeActivities()` in `src/engine/worldContent.js`) — **keep those guards**. World geography (`src/data/world.json`) stays in core.
- **3D rendering**: the Combat and Equipment screens have **no 3D view** — `CombatArena3D` and `Model3DViewer` were removed (Equipment always shows the paper doll; Combat always shows HP bars), along with `pocketEnable3D`/`Enable3dRender` and `is3DEnabled()`/`canRender3D()` in `src/utils/three3d.js`. What remains is a shared GLB/procedural pipeline other surfaces still depend on — do not delete it chasing a "no more 3D" cleanup. three.js stays vendored at `public/vendor/three/` (regen via `npm run sync:three`, never hand-edit) and lazy-loaded by `src/utils/three3d.js`'s `loadThree`/`assetUrl`/`webglAvailable`/`prefersReducedData` — the landing screen's `LandingHero3D` is the one remaining live consumer (it deliberately never gated on `pocketEnable3D`). Hero/weapon/outfit GLBs (`public/3d-samples/`, built from the CC0 Quaternius packs by `scripts/build-arena-hero.mjs` / `build-quaternius-weapons.mjs` / `build-quaternius-outfits.mjs`) and the registry `src/data/equipmentModels.json` (`weapons` + `gear` + `monsters`) are load-bearing for the open-world companion (`world/server/combat.ts`, `world/client/src/entities.ts`, `world/shared/appearance.ts`) — visual review of registry edits is still `node scripts/render-arena-hero.mjs --weapon <id> --gear <id,id>` (drives `docs/prototypes/arena-hero-harness.html`, which still imports `src/3d/heroAttach.js`). The procedural blend-shell runtime (`src/3d/blendShell.js` + `src/3d/rigs.js` + `src/3d/creatures.js` over `src/data/creatures3d.json`) is likewise kept for the open world's `procCreature.ts`; `src/3d/biomes.js` + `src/data/biomes3d.json` (arena set-dressing) survive only for `render-proc.mjs --biome`'s visual-review harness — `src/3d/biomeRegistry.js` (the arena's placeId→biome resolver) was the one arena-exclusive piece and is gone. The dormant procedural hero (`src/3d/heroCompose.js`/`heroCreature.js`/`src/data/hero3d.json`) is authorable only via `render-proc.mjs --hero`, same as before.
