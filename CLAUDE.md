# CLAUDE.md — PocketRPG Contributor Guide

> Accurate, terse instructions for AI/human contributors, loaded every session. When behaviour or scripts change, update this file in the same change. Keep it short — it's input-token cost on every session.

## 0) Orientation
- **Product**: menu-driven, tick-based, mobile-first fantasy **idle RPG**. Deterministic core; client runs the game loop locally and syncs to a server that is the source of truth for accounts, high-value grants, and competitive/social systems (§14).
- **Code**: client in `src/`, Cloudflare server in `functions/` behind the router in `worker/`, content in `src/data/`, tests in `tests/`.
- **Build**: deployed app is a generated, gitignored `index.html` + lazy `game-<hash>.js` (§12). Edit `src/**`, never the generated output.
- Pass the §11 commit gate before committing. §17 (token discipline) applies to every session.

## 1) Snapshot
- Idle/sim fantasy RPG with OSRS-style combat/skilling (PocketRPG-owned fantasy naming).
- Tick: 600ms (`TICK_MS = 600`). Goals: mobile-first UI, low-latency local play, deterministic core. Requires an account + server connectivity (auth, characters, rewards, PvP, payments all server-side).
- Hosting: **one Cloudflare Worker** (`pocketrpg-app`, `wrangler.jsonc`) serving the site, the API and both Durable Object classes. `worker/index.js` is the entry; assets are staged into `dist_site/` by `scripts/stage-site.mjs`.

## 2) Tech Stack
- **UI**: Preact + JSX (no React). Reuse `src/components/`.
- **Styling**: Tailwind v4 compiled from `src/index.css` (`@import "tailwindcss"`) by `build_single.cjs` via Tailwind CLI — not a CDN. Tokens are CSS variables in `:root`. Fonts self-hosted via `@fontsource` (latin subset).
- **Client persistence**: IndexedDB (`idb`) + `localStorage`.
- **Server**: handlers in `functions/` (Pages-style `onRequest*` exports, dispatched by `worker/router.js` — add a file, run `npm run gen:routes`) over **D1** (SQLite, binding `DB`, schema in `migrations/*.sql`). Auth is a session **JWT** (`JWT_SECRET`) via GitHub/Google OAuth; PocketRPG is also its own **OAuth 2.1** server for MCP (§15). Payments via **Stripe** Checkout (`functions/api/stripe/`).
- **Build**: Vite + TS transpile, then single-file concat (`build_single.cjs`). **Mobile**: Capacitor/iOS (`npm run build:app`). **Tests**: Vitest, logic-only (`tests/**/*.test.ts`).

## 3) Repository Layout
**Client `src/`** — `src/engine/` is pure logic, **no UI imports**:
- `engine/` deterministic logic (combat, XP, idle sim, loot) · `screens/` top-level UI · `components/` shared UI · `state/` Preact context/wiring (`gameState.jsx`) · `hooks/` Preact hooks · `cloud/` cloud sync + `/api` client · `db/` IndexedDB · `data/` static JSON content (**immutable**) · `utils/` shared helpers (`helpers.js`, prefer over redefining — §12).

**Server `functions/`** — HTTP handlers, routed by `worker/`:
- `api/**` HTTP endpoints (`/api/save`, `/api/actions/**`, `/api/coop/**`, `/api/purchase`, `/api/mcp`, `oauth/**`, `stripe/**`) · `_lib/**` shared libs (`mcp/`, `oauth/`, `game/`, `character.js`, `jwt.js`) · `.well-known/**` OAuth discovery.

**Other**: `migrations/` D1 SQL (`NNNN_name.sql`) · `tests/**/*.test.ts` Vitest · `scripts/` build/seed/maintenance · `docs/` design plans.

## 4) Gameplay Invariants
- Round with `Math.floor()`. Inventory cap = **28** slots. HP regen **+1/60s**.
- Auto-bank on full inventory; delay **5m (Agility 1) → 10s (Agility 99)**. Players can flag item *types* as excluded from auto-bank (toggle in the Inventory item modal; `autoBankExcludedItems` setting, `src/engine/idleEngine.js` `bankEverything`/`hasBankableItems`) — excluded items are skipped on every full-inventory bank trip (idle/offline/skip-hour/MCP) and never trigger an unproductive trip on their own. The live inventory-full prompt's **Deposit All** obeys the same set via `collectDepositAll` (`src/engine/inventory.js`), and when every occupied slot is excluded it dismisses instead of resolving (resolving would re-raise the prompt next tick).
- **Server-owned settings** (`SERVER_OWNED_SETTINGS` in `src/db/saveload.js`: `bossKillCounts`, `raidKillCounts`): the server owns them, so the save payload deliberately omits them — and `applySavePayload` wipes every store before it repopulates. It reads them out first and writes them back after, on the same "absent means **untouched**, never zero" rule as banked charges below. Anything else the server owns and the payload omits needs the same three lines, or every pull silently deletes it.
- **Holdings (equipment+inventory+bank) balance as a SET, and only `getHoldings()` reads them.** They are three stores that items move *between*, so a writer that rebuilds one container from a stale copy of it destroys whatever moved: a loadout preset takes the kit out of the bank, and reverting only the inventory leaves it in no container at all. Three rules. (1) **Read through `getHoldings()`** (`src/state/gameState.jsx`), never a render prop or a `useEffect`-synced ref — every mutator writes `stateRef` synchronously, so those copies are a frame behind and the 600ms background activity runner lands in that frame. (2) **A simulation's result is applied as the DELTA it produced, never as a wholesale write of the containers it started from** — `resolveIdleHoldingsWrites` (`src/engine/holdingsReconcile.js`) does this for both idle catch-up sites (visibility return, skip-1h) and is a byte-for-byte no-op when the snapshot still matches live. Those sites read the snapshot from **IndexedDB**, which lags React state by the 300ms `AUTO_SAVE_DEBOUNCE`, so they `await flushLocalSaves()` first; the tab-hide/`pagehide` handlers flush too (the beacon only covers the cloud). (3) **A whole-holdings rearrangement is durable before it returns** — `commitHoldings()` awaits the IDB flush and fires a critical push, and the preset load `holdTicks` across it. Any new action that moves items between all three containers needs all three.
- **Banked charges** (`charges` on a bank entry — trident/scythe/blowpipe/shardglass): the bank pools them into one scalar per itemId. On any bank rewrite an **absent `charges` field means "untouched"**, never zero — `preserveBankCharges` (`src/engine/bankCharges.js`) restores it inside `updateBank`, so forgetting the field preserves instead of destroys. Code that deliberately moves charges out of the bank must write an explicit number (0 included). Idle bank trips carry charges through: `bankEverything` tallies them into the sims' `chargesBanked` map, pooled onto the entry by `applyTaskResult`/`updateBankDirect` (players keep gear out of trips via `autoBankExcludedItems`, not the engine). Every manual deposit path pools charges too — `collectDepositAll` (inventory-full prompt) and `sumSlotCharges` (banking N non-stackable copies, where reading the clicked slot alone lost the rest).
- **Quest gates** run through one funnel: `questRequirementMet(completedQuests, questId)` in `src/engine/questGates.js`, shared by client, `functions/**` and `world/server/**`. Every *requirement* check calls it (equip `questUnlock`, monster/raid gates, quest prerequisites, slayer pool eligibility, shop unlocks, Adventures links, `/api/purchase`); **completion status must not** (`QuestsScreen`'s completed filter, `worldContent.js` "Already complete") — routing status through it marks every quest done and empties the quest list instead of unlocking it. The funnel exists for the **preview-only bypass**: `pocketQuestGatesDisabled` baked by `build_single.cjs` (main branch = unconditionally off, override included) on the client, `DISABLE_QUEST_REQUIREMENTS = "true"` + a non-production hostname on the server (`resolveQuestGateBypass`, installed per request by `functions/api/_middleware.js`, `worker/index.js` (world routes + the partyserver upgrade, answered ahead of that middleware), and both DO classes — a DO is its own isolate). The var lives only in `wrangler.jsonc`'s preview env block; `tests/questGateProduction.test.ts` fails the build if it reaches production config. The bypass never writes to the save.
- Combat style: Accurate/Aggressive/Defensive **+3** relevant effective level; Controlled **+1** to attack/strength/defence.
- Dragonfire: **33% proc, max 50**, fully blocked by `otherBonus.antiDragon: true`.
- **Prayer (live PvE+PvP)**: drains a pool maxing at Prayer level; each prayer drains over time, higher tiers faster (`drainPerMinute` in `src/data/prayers.json`). Empty pool → prayers off. Pool starts full per session, persists across auto-fight kills. Prayer potion restores 20, super restore 22 (live+idle). The Wilderness runs protection prayers live (§10). **Source of truth: `src/engine/prayerDrain.js`** (idle keeps its own pool in `src/engine/idleSupplies.js`).
- **Combo food**: combo consumables (flagged `combo: true`, e.g. Karam, plus every potion/brew) use a **separate combo cooldown** — one combo item may be used the same tick as one normal food, never delaying the next attack. See `isComboConsumable` in `src/engine/consumables.js`; honoured by `combat.js` (PvE) + `pvpEngine.js` (PvP).
- **Boss adds** (`src/engine/bossAdds.js`; `spawnsAdd` in `monsters.json`): a boss fields **up to `maxActive`** live minions at once (default 1; Zaryth 4), so leaving them standing is a choice with a cost. `state.adds` is a LIST and `state.addTargetIndex` selects one — **the player attacks one thing, any number of things attack the player**. Each add carries its own `attackTimer`, so a replacement never inherits the dead one's countdown. A style-keyed spec CYCLES on spawn count (`selectAddDefinition`) — reading it without one is what made only the first-listed variant ever appear. Adds drop nothing and count for nothing; killing one restarts the wait, so clearing them is a treadmill.
- **A per-swing decision belongs to the SHARED record, never to a session.** Co-op and the open world both rebuild a combat session per player per tick, so anything decided once per swing has to live on the one boss record and be pinned onto every session: the attack clock (`src/engine/roomWideAttacks.js` — `usesSharedClock` in `world/server/npc.ts` covers room-wide attackers, summoners *and* minions), each add's clock (`advanceAddAttackTimers`), and the **multi-form rotation** (`src/engine/bossForms.js` — `advanceSharedForm` on the shared record after every session has swung, `pinFormToSession` + `state.formPinned` to stop the engine rolling its own). Rolled per session, a room fought one boss per member off a single health bar: each took a different form's max hit and rolled against different defences, and the HUD showed whichever ticked last, so there was no prayer to read off the screen. A form also decides **style**, so `monsterAttackAnim`/`monsterAttackRange` take it — reading the top-level `attackStyle` left Zaryth permanently ranged in the world, with the melee and magic clips its rig ships never playing. The world rolls the next form **one tick after** the swing lands (`formAdvancePending`), not on it: the wind-up is pre-signalled `monsterWindupLeadTicks` ahead, so rolling on the swing tick animated (and, via `EntityDiff.form` → the client's phase tint, coloured) the form the boss had just *finished* using and hit with a different one. Four traps follow. (1) A session's own `monsterAttackTimer` is then pinned to 0-or-full and **never counts down**, so anything reading it as a countdown breaks silently — the swing-animation pre-signal must read `npc.attackTimer` (`signalSwing`), and for the same reason it is signalled from the npc's own state rather than gated on one player's reach, or whichever session runs last wipes the clip for the room. (2) The flag must be cleared when the npc leaves combat, or a stale `true` buys a free opening swing on re-engagement. (3) **Nothing may write a session's copy of a shared clock back onto the record** — co-op's `processCoopTick` re-pins each add's `attackTimer` from `roomAddTimers` when the target member's session writes its add list back, because the copy it holds is the pinned value; without that the countdown is overwritten every tick, never reaches zero, and the minions never swing at all. (4) A session's add list merges back **by `instanceId`, never by index**: the engine splices a killed add out of its own list, so on the one tick that matters every add behind it shifts a slot — read positionally, a non-target member's kill was invisible and the survivors' health was compared against the wrong add's.
- **World minions are real npcs** (`world/server/minions.ts`), not session-local adds: the world's `createCombatState` call is the only one passing no monsters table, so the engine's own spawn is off out there and `mirrorOtherAttackers` (`world/server/combat.ts`) mirrors the npcs onto every session's `state.adds` instead. A boss and its minions are ONE encounter — `countsAsEngaged` keeps every part of it engaged with whoever is fighting any other part, which is both what stops "kill the add" switching the boss off and what gives a minion a target to walk toward. **Every npc keeps its quarry** where it used to let go on a disengage — trash, dragon or boss alike: `reselectAttacker` builds its engaged list from players whose own session is still fighting, and `stepCombat` ends that session the moment they are beyond both reaches — so releasing there made backing off a free reset (an unclaimed npc heals in `OUT_OF_COMBAT_HEAL_TICKS`, and a boss's minions despawn with it). A sentinel inherits its summoner's target, never having had one. Released by leaving the zone, breaking leash, or 50 ticks unable to path a step toward them (`chaseStalledTicks` — without it a quarry standing somewhere unreachable pinned the npc in combat for good). Only the LEASH is boss-tuned (`isBossFamily`; 24 tiles vs 10 — a boss's lair is much bigger than a pasture), and **inside its own instanced lair a boss has none at all** (`ctx.lair`): no radius measured from the throne bounds a private room with one door, so retreating toward the way in (Zaryth's is 25 tiles out, the far corner 28) snapped it home at full health mid-fight. The room bounds the chase and leaving it releases aggro. That makes the out-of-combat heal `giveUpPursuit`, snapping the npc home too — with no leash to guarantee it, a boss ends its fights wherever the chase left it, outside the wander rect where it can take no step at all. Keeping the target is dead weight without `resumeAggro` (`world/server/combat.ts`, called from `tickPlayer` before `stepCombat`): a chased-down player has no live combat session (theirs ended when they walked out of reach), and an npc's swings only ever resolve inside one, so without this a pursuer would jog alongside its quarry forever, visibly hunting, landing nothing. This does not reopen unprovoked fights — it only fires for an npc whose `attackerId` is already this player (set by nothing but a prior `startCombat`), so a monster the player never clicked still starts nothing on its own (`combat-flow.test.ts` "stays out of combat standing next to an idle monster"). The resumed session is **active**, not the passive kind a walk-away disengage leaves — it caught you, this is the real fight. Each mirrored attacker is gated on **its own** reach, never the session npc's, and **wears its npc's current form** — a mirror left on the raw `monsters.json` row carries no `formMaxHit`, so `monsterMaxHit` falls through to its derived branch and a player who turned on a sentinel took 212 from a boss whose hardest form hits 60, in the top-level style whatever form the room could see.
- **A world death is settled AFTER the tick's diff goes out** (`WorldZone.tick` collects `deaths`, then `respawnPlayer` runs past `broadcastDiffs`): every death path either heals the player to full or drops them from `this.players`, and the broadcast only reaches players still in that map — settled inline, the killing blow's splat and the emptied bar went to everyone except the player who died, so you died with health to spare and an instanced lair (Zaryth) showed nothing at all. The 0 rides `stepCombat`'s own `{e:'hp'}` so no future reordering can lose it; `endOneLifeRun` fires at the same point because its message drains from `pendingEvents` before the broadcast. A dying player is skipped by the loot and exit-tile loops in between. World HP stays a session resource either way: entry seeds it at `maxHp` and no flush writes it back to the save.
- **Boss entry gates are server-authoritative and kill counts are NOT in the save** — they live in D1 `kill_counts` (§14). One funnel: `functions/_lib/game/bossEntry.js` (`bossEntryFailure`, `bossHasEntryGate` to skip the D1 work for an ungated lair). Whether a boss is gated at all is `hasKillCountGate` (`src/engine/combatRequirements.js`), **never the raw `killCountRequirement` field** — the Ashen Crucible's Ember Tyrant prerequisite is hardcoded in the engine, so a field check reads "ungated" and skips the query that would enforce it. On the CLIENT the counts arrive a fetch after the rest of the state, so every gate check takes `bossKillCountsLoaded`, and while it is false a gated boss answers `{ locked, pending }` — "checking your kill counts", not a verdict. Both verdicts are wrong in that window: "unmet" tells a player who cleared the prerequisite long ago to go and clear it, and "met" dresses a world-map hub row as available so the tap is refused a moment later. Callers surface `pending` as news, not as a refusal (`WorldMapScreen`'s `activateActivity`). The **slayer pool is the deliberate opposite** — `isEntryEligible` fails CLOSED on counts it cannot see, because an unverifiable count there hands out a task nothing will start; that is an assignment policy, so anything merely DISPLAYING a lock uses `meetsEntrySkillAndQuestGates` + its own kill-count check instead.
  - **Who writes a kill count, and for which monsters — every monster earns one, from four writers.** (1) A server-authoritative completion (`_completeShared`): bosses and collection-logged monsters. (2) The **open world**, for every monster (`recordKillCounts`, `world/server/bossKills.ts`) — it resolves its own combat, so nothing is client-trusted out there. (3) **Co-op**, per settlement. (4) The **idle game**, for ordinary monsters only, CLIENT-REPORTED as a `kills` side channel on `/api/save` (`src/engine/killTally.js` → `functions/_lib/game/killCounts.js`), because a grind cannot cost a cloud write per cow (§6). (2)–(4) are **batched**; never add a round trip per kill anywhere.
    - **What makes (4) safe is `isClientReportableMonster`** (`src/engine/killCountReports.js`), and all three of its exclusions are load-bearing: a boss and a logged-drop monster are already counted by their own authoritative completion (reporting them DOUBLE counts), and **anything named by a kill-count gate is refused outright** — that set is derived from the content via `killCountRequirementsFor`, the same funnel `unmetKillCountRequirement` uses, so the Ashen Crucible's hardcoded Ember Tyrant prerequisite is in it. Nothing a client says may open a boss door (§14). What is left is monsters whose XP and loot already ride the trusted blob from the same kill. The tally settles by subtraction on an ok (mirroring `lossLedger.js`) and is applied past every guard in `applySaveWrite`, so a REFUSED save counts nothing and the client's retry cannot double-count.
    - **The collection log is gated on the DROP, not on the monster.** `recordBossKill` fills a slot for any monster that owns one — a Black Dragon's visage is a logged unique and its killer is not a boss — so a `boss` gate there left exactly those slots unfillable in the world. `uniqueDropsFrom` is a pure filter, so an ordinary kill with nothing logged reaches no D1 at all. The kill count is not in that function; don't put it back. **Co-op counts the kill for everyone who fought it** (`killCountCharacterIds`: alive, damage > 0), not just the 10% loot winners — the damage gate exists to stop a drop table being farmed, and a kill count is not a drop. Non-winners are claimed through the same `coop_kill_settlements` key (with `granted_json = '[]'`) and **after** the loot shares: both claims share one table, and on a D1 still carrying 0031's `(session_id, kill_seq)` key the first row written takes the only slot.
- **Hard Mode** (`src/engine/hardMode.js`, opted into per boss/raid by `hardMode: true` in the content): scales the monster record + the whole monsters table at the door (`monstersTableFor`), so no combat code branches on it; `hardModeActive` marks a scaled record, and the ACTIVE TASK persists it. **`hardModeActive` is the ONLY honest answer to "was this fight hard", and it lives on the record the fight was BUILT from** — never on a `monsters.json` lookup, which is what `resolveMonsterRewardData` returns for the reward tables. Reading the flag off that always answered "no", so Fight Again and Skip restarted an *ordinary* boss while the server's switch kept paying doubled rates; the loot modal therefore carries its own `hardMode`. Drop rates are the deliberate exception, server-side only (§14) — and because the switch is D1 and the client holds a mirror, the two can legitimately disagree, so a completion **reports what it fought and the server takes the lower of the two** (`hardModeForKill`): the body can turn the doubling OFF, never ON, and an absent field keeps the server's answer so an older client never silently stops being paid. The mirror is also part of the **`killCountsLoaded` gate** (`App.jsx`) rather than a fetch alongside it — the combat screen auto-starts the instant that flips, and a fight built before the mirror lands is an unscaled boss. **The death penalty must fire on every path a hard fight can kill you**: solo (`CombatScreen`) and the co-op/raid room (`processCoopTick` — one code path, boss and raid alike). The three idle sim sites carry it too (`resolveIdleHoldingsWrites`'s `hardModeDeath` option, never a second write that would race the §4 reconcile), but that path is **unreachable today and deliberately kept**: every `hardMode: true` monster is `boss: true` and `simulateIdleCombat` returns null for a boss, so it only goes live if a non-boss ever opts in. **Untradeables are never lost** (`survivesHardModeDeath`) — an Infernal Cape cannot be bought back, so losing one ends the account's relationship with that content; coins are the one exception to the exemption, flagged `isUntradeable` only for the store engine (same artefact `lootTransfer.js` special-cases). A raid **wipe returns the party to the lobby on the death tick**, so `CoopBossScreen` builds the death modal before the lobby early-return and renders it from both branches — §21's rule for the loot modal, same trap.
- **Boss Slayer XP**: `BOSS_SLAYER_TASK_XP_MULTIPLIER` (×4) in `src/engine/slayerRewards.js`; avoid inflated explicit `slayerXP` on bosses (keep XP/hr ≤ ~2× best regular monster).
- **Slayer masters** live at world places (`placeId` in `src/engine/slayerMasters.js`, surfaced as worldContent's `slayer` activity kind). Getting a task is a place action — away from the master it opens the travel prompt; arrival auto-assigns via the Slayer screen (`initialMasterId`). Slayer point unlocks are bought on the Character Unlocks screen, not the Slayer screen.
- **A slayer task advances wherever the kill happens.** One funnel for the arithmetic — `creditSlayerTaskKill` (`src/engine/slayerKillCredit.js`), pure so a Durable Object can run it — used by the solo screen, co-op (`creditSlayerKill`, alive members only, damage-independent) and the open world (`creditWorldSlayerKill`, `world/server/killProgress.ts`). Both server contexts hold the task on the SESSION and hand it back the same way: the task is state and is written outright, points/completions are **deltas** added and then cleared (`applySlayerCreditToSave`, `functions/_lib/game/slayerCredit.js`; an absent `slayerTask` FIELD means "untouched", never "cancel it"). The world only writes it once a kill has moved it (`dirty`), and a failed flush restores the delta rather than dropping it.
- **Auto Slayer Task** (`auto_slayer_task`, 100-credit Character Unlocks purchase; server debit in `functions/api/unlocks/purchase.js`, owned-flag `characterUnlocks.autoSlayerTask` in the save): while idling *on* your assigned slayer monster, catch-up/skip re-assign the next task from the **same master** and keep simulating until the window (or supplies) run out, instead of farming the finished monster off-task. Chain lives in `src/engine/idleSlayerLoop.js` (`simulateIdleCombatChain` wraps `simulateIdleCombat` + its `stopOnSlayerComplete` option); it aggregates per-task points via `resolveSlayerLoopRewards` and per-monster kills/loot via `perMonster`. Rolled boss tasks can't be idled → the chain stops and leaves the boss task assigned (no reroll). Wired into the 3 client combat-sim sites only (boot `gameState.jsx`, visibility-return + skip-hour `App.jsx`); the MCP `idle` intent path is **not** chained. On modal close the idle-result handler resumes live combat on the new monster (`chainCombatResumeTarget` + monster-keyed `CombatScreen` remount) and teleports the player to its world place (`placesForActivity`) — the sim ignores travel, so arrival is instant; boss/death end-states don't auto-resume.
- **Kingdom of Royals** (Adventures screen, unlocked by quest `crown_complications`): deposit coins into a coffer (cap 25m, drains at a flat 5m/24h whenever any labour is allocated, ~5 days runtime) and allocate 4 labour points across Mining/Fishing/Woodcutting/**Farm Herbs** — the last is gated and tier-weighted by **Farming** level, not Herblore (`src/engine/kingdomResources.js` derives its ladder from `farming.json`'s herbs). Output is ordinary commodity resources (no uniques/credits) so it's **client-trusted** like idle catch-up, not server-authoritative — `src/engine/kingdomEngine.js` `simulateKingdom` runs independently of the active-task idle dispatch, keyed off its own `kingdom.lastTickAt` (boot, visibility-return, skip-hour, and a live 60s tick all call `settleKingdom`). Coffer drain is flat regardless of point count (funds the kingdom, not per-worker wages) — don't scale it by allocated points. Gathered output does **not** auto-bank: it accumulates in `kingdom.pendingLoot` (`mergeLoot` folds each settle's `itemsGained` in) and the player withdraws it manually from the Kingdom screen's loot modal (`withdrawAllLoot`) — don't wire `settleKingdom` back to `updateBankDirect`.
- **Construction unlockables + passive perks** (`UNLOCKABLES` in `src/engine/construction.js`, incl. the Lv 80 gather auto-bank perk) are bought/shown on the Character Unlocks screen, not the Construction screen — same pattern as Slayer point unlocks above. Gather auto-bank only applies during idle/offline catch-up and skip simulations; live gathering still stops on a full inventory.
- **Daily Tasks**: 5 tasks/day (one per tier: Novice → Grandmaster), reset **00:00 UTC**, **+1 credit** each. Server-authoritative grant, **never** via `/api/save`: one atomic claim (`claimDailyTaskCredit`, `functions/_lib/game/dailyTaskProgress.js`) behind both `/api/daily-tasks/complete` and the progress path, so whoever reaches the target pays and a replay pays nothing. Issuance is lazy on `GET /api/daily-tasks`; durable table `character_daily_tasks` (migration 0025, outside the save blob). Cloud accounts only (mirrors credits pill). Event bus: `recordGameEvent(evt)` in `gameState.jsx`; matcher: `src/engine/dailyTasks.js`.
  - **PROGRESS is server-side, and callers send EVENTS, never a number.** `applyDailyTaskEvents` matches them against the character's own issued rows with the client's matcher; the client mirrors its matched events to `POST /api/daily-tasks/progress` batched (8s debounce + tab-hide), and the open world's flush posts its own (`world/server/killProgress.ts`). It lived only in the client's memory before, so a reload lost it and a kill made where that client is not running — the world is its own tab and its own DO — could never move a task. Two rules follow. (1) A same-day re-fetch is a **floor, not a replacement** (`setDailyTasks`, and the flush's own merge): events matched locally since the last push are already in the local number, and the server's older one would undo them. (2) The client's optimistic update is display only — the server does the arithmetic, so a batch is safe to drop rather than retry.
  - **Co-op credits its own daily tasks client-side** (`CoopBossScreen`), because the room has no idea what today's tasks are and every member is running the idle client. The room names who fought each kill (`killCountCharacterIds` on `bossDefeated`/`raidBossDefeated`/`raidComplete`) and `foughtThisKill` gates on it — an absent list means a room older than the field and answers **yes**, or a deploy silently stops paying the party. Solo parity: every raid boss is a `boss_kill` and the clear is also a `raid_complete`.
- **Journeys & teleports**: clues/quests run **only** as world-map journeys (`src/engine/journeys.js`; content granted on the final search; auto-chains next scroll / quest queue in `App.jsx`; legacy timer tasks still tick out). Per-place Magic teleports in `src/data/world.json` `teleport` (cities low — Varrick 25 — villages up to 87; always law runes; XP = level+10; `src/engine/teleports.js`); mid-journey teleports re-plan the walking leg, searches are pinned to their waypoint.

## 5) XP & Leveling
- Levels **1–99**. XP cap **200,000,000**.
- `totalXP(L) = floor(sum(x=1..L-1, floor(x + 300 * 2^(x/7)) / 4))`.
- Starting HP level **10** (1,154 XP).
- Gains: Combat **4 XP/damage** to primary skill, **1.33 XP/damage** to HP. Magic: base spell XP + **2 XP/damage**.

## 6) Combat Tick Model
- Tick **600ms**.
- Melee max hit: `floor(0.5 + effectiveStr * (bonus + 64) / 640)`.
- Accuracy: `maxRoll = effectiveLevel * (bonus + 64)`; if `attackRoll > defRoll`: `1 - (defRoll + 2)/(2*(attackRoll + 1))`, else `attackRoll/(2*(defRoll + 1))`.
- Auto-fight restart delay after kill: **1.2s**.
- **Only a boss or a raid stops the game on the full-screen `LootResultModal`** (`killPresentsFullModal`, `src/utils/lootModal.js`). An ordinary kill flashes its loot as a reward-reveal card (`emitKillReveal`) and re-arms itself after the delay above — a grind must not need a tap per cow. A server-authoritative ordinary kill (non-boss with a collection-logged drop) simply holds the fight for the round trip — that hold is also what stops two `completeMonster` calls overlapping.

## 7) Special Attacks
- PvE special energy (`combatState.specialAttackEnergy`) **0–100**: starts each fight at 100, drains on use, refills on kill.
- Manual trigger only (`⚡ Special Attack`). No automatic/offline firing. Adding one → skill **`add-content`**.
- **The open world deliberately diverges**: energy is a persistent *session* resource there, never refilled by a fight ending or a kill — it only regenerates on the clock (`SPECIAL_REGEN_PER_TICK`, 10 per 30s, `world/server/tick.ts`). `player.specialEnergy` is the truth and is pushed onto the engine state each tick (`pinSpecialToSession`), because the shared engine still resets its own value on kills/phase resets. Don't "fix" the world back to the per-fight model above.
- **Master Rejuvenation** (`master_rejuvenation`, the Lv 90 Construction perk) **refills** the bar to 100 the moment it empties — `refillSpecialOnEmpty` (`src/engine/specialRegen.js`), called by all three contexts that own a copy of the energy: solo (`CombatScreen`, mid-fight only), every co-op/raid member (`processCoopTick`, in every phase — lobby and respawn wait are prep time), and the world (`tickPlayer`). The flag is read from `settings.unlockedFeatures` once per context (client Set, co-op member at join, world player at hello). **The Wilderness is the one place it is off** (`ctx.pvpZone` from `isPvpZone`, §10) — a bar that comes back free decides a duel by who owns a perk. **Empty means the bar READS 0% (`energy < 1`), not an exact zero** — solo and co-op hold whole points, but the world's energy carries the fraction of its 0.2/tick clock regen and a flat cost off 50.2 leaves 0.2, so `=== 0` fires approximately never out there. For the same reason the world applies it BEFORE the clock regen, on the same tick `stepCombat` spends.

## 12) Single-file Build Safety
- `index.html` is generated by `build_single.cjs` and gitignored (`/index.html`, `/game-*.js`) — never edit/commit it; change `src/**`. `npm run build:site` rebuilds it, builds the world client and stages both into `dist_site/` (also gitignored) for the Worker's `assets` binding.
- Top-level declarations must be **globally unique** across both output files; duplicate-identifier errors are release-blocking. Prefer `src/utils/helpers.js`.
- **No eval-time cross-module reads**: the scripts run top-to-bottom in `sourceFiles` order, so a module's **top-level** `const`/`let` initializer must not read a binding another module exports (e.g. `const IDS = new Set(SLAYER_UNLOCKS.map(...))`) — if that module is concatenated first, the import is in its temporal dead zone → `Cannot access X before initialization`, which aborts the whole inline script and whites out prod. `node --check` can't see it; `check:single` now executes the bundle to catch it. Fix by deferring the read into a function (lazy init), never by reordering `sourceFiles`.
- **Code-split**: two CLASSIC scripts (not modules) — inline core in `index.html` + content-hashed `game-<hash>.js` (heavy in-game screens, `GAME_CHUNK_FILES`), loaded lazily on `cloudPhase === 'ready'` via `globalThis.__loadGameChunk`. Classic scripts share one global lexical env; cross-refs resolve by source name. Both minify with `minifyIdentifiers: false` — **do not re-enable**.
- New in-game screen → add to `sourceFiles` **and** `GAME_CHUNK_FILES`. Landing/auth-reachable screens stay **out** of `GAME_CHUNK_FILES`; core must not reference a chunk binding at module-eval time (only inside `renderScreen`).
- `gameIconsData` (~126 KiB) and `worldActivitiesData` (~150 KiB, `src/data/worldActivities.json`) are in the chunk. Core code guards every access (`typeof gameIconsData !== 'undefined'` + emoji fallback in icon code; `placeActivities()` in `src/engine/worldContent.js`) — **keep those guards**. World geography (`src/data/world.json`) stays in core.
- **3D rendering**: the Combat and Equipment screens have **no 3D view** — `CombatArena3D` and `Model3DViewer` were removed (Equipment always shows the paper doll; Combat always shows HP bars), along with `pocketEnable3D`/`Enable3dRender` and `is3DEnabled()`/`canRender3D()` in `src/utils/three3d.js`. What remains is a shared GLB/procedural pipeline other surfaces still depend on — do not delete it chasing a "no more 3D" cleanup. three.js stays vendored at `public/vendor/three/` (regen via `npm run sync:three`, never hand-edit) and lazy-loaded by `src/utils/three3d.js`'s `loadThree`/`assetUrl`/`webglAvailable`/`prefersReducedData` — the landing screen's `LandingHero3D` is the one remaining live consumer (it deliberately never gated on `pocketEnable3D`). Hero/weapon/outfit GLBs (`public/3d-samples/`, built from the CC0 Quaternius packs by `scripts/build-arena-hero.mjs` / `build-quaternius-weapons.mjs` / `build-quaternius-outfits.mjs`) and the registry `src/data/equipmentModels.json` (`weapons` + `gear` + `monsters`) are load-bearing for the open-world companion (`world/server/combat.ts`, `world/client/src/entities.ts`, `world/shared/appearance.ts`) — visual review of registry edits is still `node scripts/render-arena-hero.mjs --weapon <id> --gear <id,id>` (drives `docs/prototypes/arena-hero-harness.html`, which still imports `src/3d/heroAttach.js`). The procedural blend-shell runtime (`src/3d/blendShell.js` + `src/3d/rigs.js` + `src/3d/creatures.js` over `src/data/creatures3d.json`) is likewise kept for the open world's `procCreature.ts`; `src/3d/biomes.js` + `src/data/biomes3d.json` (arena set-dressing) survive only for `render-proc.mjs --biome`'s visual-review harness — `src/3d/biomeRegistry.js` (the arena's placeId→biome resolver) was the one arena-exclusive piece and is gone. The dormant procedural hero (`src/3d/heroCompose.js`/`heroCreature.js`/`src/data/hero3d.json`) is authorable only via `render-proc.mjs --hero`, same as before. ## 14) Production Security Model
Server is source of truth for everything that *can* be authoritative. The one deliberate exception: the save blob — no server-side engine recomputes the tick loop, so the client computes XP/coins/drops and the server trusts them. Know which side owns a thing before changing an endpoint.

**Server-authoritative (integrity boundary — never move to client/save):**
- **Identity & ownership** — auth (session JWT via `requireAuth`), characters, OAuth; every `/api/*` route verifies the token.
- **High-value grants** — boss/raid/clue/minigame/dungeoneering uniques granted by `/api/actions/**` (server-side loot RNG, kill-counts, collection-log, nonce replay protection). Save only carries the already-granted item.
- **Purchases** — `/api/purchase` debits coins + grants server-side. **Credits** — debited atomically by `/api/skip-hour`, `/api/slayer/skip`, and `/api/daily-tasks/complete`; **never** from `/api/save`. Skip-1h also covers travel/journeys: exactly one hour of trail time — longer journeys park mid-trail (never complete in full); time left after a completion chains further scrolls/queued quests.
- **Daily task credit grants** — `/api/daily-tasks/complete` atomically flips `credited=0→1` (idempotency key) then increments `credits`; replay returns `creditsGranted: 0`.
- **Wilderness settlement / trading post** — own server-authoritative paths (§10).
- **Co-op boss fights** (`/api/coop/**`, §20) — the server resolves every swing, so XP, supply consumption and the kill's loot roll/grant are all authoritative, not save-blob.
- **Admin grants** — `POST /api/admin/grant-item` puts any item/quantity into any character's inventory or bank; `/admin` is its UI (`functions/admin.js` + `functions/_lib/admin/portalPage.js`, fed by `/api/admin/catalog`). Admin auth for all of it is the deploy-time **`ADMIN_SECRET`** via `X-Admin-Secret` (`functions/_lib/adminAuth.js`, constant-time, fails closed when unset or under 16 chars); a session JWT grants nothing there, and the `/admin` document ships the gate only — every list and every capability is behind a server check, so unlocking can't be faked from the DOM. `POST /api/admin/restore-save` (same auth) lists/inspects/restores a character's preserved save blobs, `POST /api/admin/snapshot-save` forces one on demand — the only admin write that skips the save locks, because it only reads the stored row — and `GET /api/admin/item-loss` is the Incidents queue, every `item_loss_detected` event joined to the snapshot that undoes it (`save_history.save_revision === payload.previousRevision`). Its `POST` files the admin's verdict into `item_loss_reviews` (migration 0037, keyed on the audit event id): `dismissed` (detector false positive) or `confirmed`, `open` to undo — which DELETEs, so the absent row is the third state. **Both verdicts are recorded, not just the dismissal**: shadow mode only ends when the false-positive rate is a query, and it is unanswerable while "not a loss" and "nobody has looked yet" are the same row. Dismissed rows leave the default list but are never deleted, and that filter runs in **SQL** — applied after the `LIMIT` it returns a short page whenever something recent was dismissed. Grant and restore respect all three save locks and the revision guard — the grant is the server twin of `scripts/grant-save-item.mjs` (skill `save-item-grant`). The portal is deliberately outside the Tailwind/`build_single.cjs` pipeline (it must load with no account and no game chunk), so its Forgemark tokens are **mirrored** from `src/index.css` — update both when DESIGN.md §3 changes.
- New economy/progression mutations must emit **audit events** (`functions/_lib/game/audit.js`).

**Client-trusted (the save blob — deliberate, bounded):**
- Live skilling, idle/offline catch-up, skip-hour compute XP/coins/drops client-side and persist via `/api/save`. XP/coins + client-created items (idle/offline loot, crafted/smithed/cooked products, skill capes) ride the trusted blob since those paths legitimately create them and the server has no engine to re-derive them.
- Leaderboard is best-effort, not cheat-proof. Do **not** add `/api/save` checks policing economy/item *increases* — they break the core loop and buy no real protection. Tighten integrity by moving a reward onto a server-authoritative endpoint, not by validating the save.
- **Item-loss safety net** (`docs/item-loss-safety-net.md`) — a preset bug once wrote a stale holdings container over the live one and ate most of a bank; the guard meant to catch it (`detectBankWipe`) missed because it counts distinct bank **ids** at a 90% threshold, sees no quantities, and runs only on `/api/save`. Three pieces now sit under **every** save writer. (1) `save_history` (migration 0036, `functions/_lib/game/saveHistory.js`) preserves the blob each write overwrites — an `INSERT ... SELECT` off the `saves` row that must stay **first** in the batch, since D1 runs a batch in order. Recovery is `/api/admin/restore-save` (the `/admin` Salvage panel), which writes the snapshot's content **forward** as the next revision rather than rewinding `save_revision`. (2) `functions/_lib/game/holdingsDelta.js` measures what a write destroys across bank ∪ inventory ∪ equipment and audits it as `item_loss_detected` — **shadow mode: it rejects nothing**, so the guard list below is unchanged. Its baseline is captured in `hydrateCharacterSave` and carried in a WeakMap because every server writer mutates its save in place; a caller writing a **rebuilt** save object (co-op's `applyMemberToSave`) must pass `baselineFrom` or it is silently skipped. Classification is by items.json `type`, never `stackable` — food and materials are non-stackable but consumed in bulk. (3) **The declared loss ledger** (`src/engine/lossLedger.js`, Phase 3a) nets deliberate spends off (2) before it thresholds, because production idling spends recipe inputs by the thousand and a durable ingredient — a summoning infusion's `steel_platebody` — flagged nearly every save, which is a queue nobody can read. It rides the PUT/beacon body as `losses` (a side channel: nothing is stored, so the save format and `noopSaveKey` are untouched), settles by **subtraction** on a successful push (a spend made while that push was on the wire belongs to the next save) and **resets** on `applyCloudSave` (the server superseded that window). Netting is per item, clamped at zero, and measured from what actually LEFT the container — `bankUnitsRemoved`, `applyTaskResult`'s `consumed` — never from the delta that was requested, or a real loss hides behind the over-declaration. Only itemised mutators declare — the deliberate destructions the player asked for: a hard-mode death (all four client sites, plus co-op's, which banks on the MEMBER and is spent by the save write-back via `writeSave`'s `declaredLosses`, because the room takes the pack inside the DO where no client ledger can see it), charging an item with its charge material (`chargeRecipeSpend`), combining two items into a third, and dropping or breaking down a slot (`slotUnitsRemoved`). (`updateBankDirect` negatives; server-side, `declareItemLosses` onto the save, keyed like the holdings baseline and **cumulative from the load**, because the baseline is captured once in `hydrateCharacterSave` and every `writeSave` on that request measures against it — `trading-post/list.js` writes twice around matching); **a wholesale container write declares nothing by construction, which is the entire mechanism** — never add a declaration to a path that rebuilds a container from a snapshot. The trading post's escrow declares (goods are *moved* into the book, but bank ∪ inventory ∪ equipment is all the detector sees), placed with the removal and only after it succeeds — a refused escrow that declared would cover a real loss of the same item on a later write. Still shadow mode: rejecting needs the coverage of Phase 3b, specced in the doc; don't add rejections here without it.
- `/api/save` enforces exactly **three** anti-cheat-adjacent guards (integrity, not anti-cheat): stale-write rejection (`save_revision`), the total-level regression guard, and the bank-wipe guard (both in `functions/_lib/game/saveValidation.js`). Separately, saves are **locked** entirely during an active co-op boss session (§20) and during a live open-world session (`world_sessions`, migration 0030; `functions/_lib/game/worldSessions.js`) so the companion app and idle game never write the same save at once — the world DO holds the lock (begin on hello, heartbeat refresh, clear on disconnect; TTL self-heals a dead DO) and the world's own grant flush is the sole path that mutates the save while it's held. **Releasing it fast is a feature**: the world runs in its own tab, so a player who switches back to the idle game is blocked from saving until it lapses. Four paths keep that short — a closing tab departs **immediately** via both a `leave` frame and an out-of-band exit beacon (`POST /api/world/leave` → `departCharacter` RPC; the frame may never flush during unload, so the beacon is what makes closing the browser equal pressing Log out), the client departs after 10s hidden (`world/client/src/away.ts`), a closed socket lingers only `LINGER_TICKS` (≈10s) before flushing and releasing, and that close also back-dates the row (`expireWorldSessionAfter`) so an evicted DO can't hold the save for a full TTL. Don't lengthen any of them. **One exception, and it is not negotiable either way: a player IN A FIGHT does not leave** (`world/server/combatLogout.ts`) — every exit (Log out, `leave` frame, exit beacon, dead socket) becomes a frozen, still-killable body until combat has been over for `COMBAT_LOGOUT_BLOCK_TICKS` (≈10s), capped at `COMBAT_LINGER_MAX_TICKS` (60s) so a bug or a patient attacker can't sit on the lock; that linger keeps the heartbeat running, and `expireWorldSessionAfter` is armed to the cap rather than the linger, or the save unlocks while the body is still on the field.

## 17) Token efficiency (mandatory, every session)
In-session discipline mirroring Headroom's mechanical savings. Deviate only when the user asks for more detail.

**A) Output shaping** (the most-violated rule — obey literally):
- Lead with the answer/result. No preamble, postamble, or restating the question/plan/what you just did.
- Budget ≤6 lines for routine replies; post-edit status is 1–3 lines. Exceed only when asked, or when correctness needs a table/steps/code — then still cut dead sentences.
- Never echo context the user can see (file contents you edited, tool output, diffs, commands, their request) — point to it (`save.js:146`).
- No step narration, no closing recap, no unprompted "what I changed and why".
- One idea per line; cut filler. If a sentence survives deletion without information loss, delete it.

**B) Effort routing**: minimal reasoning on routine/mechanical work; deep reasoning only for novel/ambiguous problems.

**C) Intake reduction**: read narrowly (targeted `Grep`/`Glob`, `Read` with `offset`/`limit`); prefer `files_with_matches` before `content`; don't re-read files in context or re-derive known facts; batch independent calls; fetch on demand, not just-in-case.

**Local sessions only**: run `npm run claude:headroom` (`scripts/headroom-claude.sh`) for actual Headroom compression + output shaping (`HEADROOM_OUTPUT_SHAPER=1`; prereq `pip install "headroom-ai[all]"`; see `HEADROOM.md`). This wraps Claude Code at launch locally — it cannot reroute Claude Code Web/cloud sessions, so the rules above carry the load there. Don't commit `ANTHROPIC_BASE_URL` to shared settings.

## 20) Co-op Boss Fights (`/api/coop/**`)
Several players versus one shared boss, in the idle game. **Allowlisted per boss** (`COOP_BOSSES` in `src/engine/coopBossEngine.js`): every boss in `monsters.json` **except raid bosses** (which are group-playable only inside a raid party, §21) and the solo-only four — the Ember Pits pair `ember_tyrant`/`ashen_crucible`, plus `venomcoil_matriarch` and `blighted_gauntlet`. Keep it an explicit list, not a filter over the monster data, so opening a boss to groups stays a deliberate edit. The wait between kills is **flat: `COOP_RESPAWN_TICKS` = 8 ticks / 5s for every boss** (8 because the HUD renders `ceil(ticks * 0.6)`, so 8 is the longest wait still reading "5s") — a deliberate replacement for the old per-boss `clamp(round(12750 / hitpoints), 10, 100)` curve, which paced the farm loop off the boss's HP (Grondar 255 HP → 30s; the Horror 2000 HP → 6s). One predictable number beats a curve players cannot see, but it does mean a squishy boss's GP/XP per hour is no longer held back by its respawn: pace a new co-op boss with its drop table or its HP, **not** by reintroducing a per-boss delay.
- **Picking solo vs group**: tapping an allowlisted boss in the combat picker opens a choice prompt (`coopChoice` in `CombatScreen.jsx`) — solo runs the normal client-side fight, group joins a server session. Any other entry point into `startFight` (auto-start, slayer, dungeon) stays solo.
- **The group fight must look like the solo fight.** `CoopBossScreen` renders the same mobile HUD as `CombatScreen` — back link, fight header, HP blocks, prayer bar, `CombatQuickActions`, `cb-actions` row — and the shared blocks live in `src/components/CombatHud.jsx` so the two cannot drift. Add HUD markup there, not to one screen. A kill shows the same `LootResultModal` as a solo boss (shaping shared via `src/utils/lootModal.js`) to each loot winner, and the respawn wait shows as a live countdown. Two deliberate co-op-only surfaces exist. First, the **loot share bar** (`src/components/CoopLootShare.jsx`, `.cb-loot-*`), a hairline track under the boss's name in `CombatFightHead`'s `meta` slot: it exists because the 10% threshold made "am I getting a drop" a decision the player has to make mid-fight. It measures the player's OWN damage against the *threshold*, not the boss's health — so it fills across the 0–10% they need and turns solid verdigris at "drop secured". It started as a full roster panel of every member and that was **too tall for a phone**; keep this a glance, not a scoreboard. Deliberately absent: any per-member damage table, and any Leave button beyond the standard back link. Second, **fight chat** (`src/components/CoopChatPanel.jsx`, `.cb-chat-*`) — same 44px band open or shut, because shut it is the newest line and a purple-drop announcement has to land in front of a player who never opens the log. **The respawn wait is prep time**: `processCoopTick` applies intents *before* the respawn early-return, so the group can eat, drink and swap gear between kills — and because no combat resolves during the wait, `tickIdleCooldowns` walks the consumable cooldowns down by hand (without it one bite blocks the rest of the wait). Server-side gaps show as parity gaps, so every quick-action needs its intent: `equip` enforces level/quest gates against the `levels`/`completedQuests` the member carries from join (fails **closed** — a session predating those fields equips nothing gated) and refuses rather than drops gear when a 2H swap won't fit the pack.
- **The fight runs in a Durable Object**, not on D1. `CoopBossRoom` (`world/server/CoopBossRoom.ts`) holds the state in memory and advances it on its own 600ms `setInterval`; `/api/coop/session/[id]/{tick,intent,leave}` are authenticated thin proxies (`functions/_lib/game/coopRoom.js`). D1 is written on join, leave, kill settlement and a 25-tick checkpoint — **never on an ordinary tick**. Migrations 0031 + 0032. The class is a **local export of the one Worker**, bound as `COOP_ROOM` (`wrangler.jsonc`). It used to live in a second Worker and be bound cross-script, because a Pages project cannot export a DO class — that is where the two-deploy rule, the `coopRoomsAvailable`/`COOP_UNAVAILABLE` degradation and the raid capability probe all came from, and all three are gone. **Don't reintroduce a split**: `CoopBossRoom` is called only from `/api/coop/*`, so hosting it elsewhere puts a network hop between a route and the object it drives, and lets the two versions disagree. **A tick is published only once nothing more can be appended to it** (`publishedTick`, advanced in `tickInner`'s `finally`; `eventsSince`'s `untilTick`). Events are keyed by tick and a client acknowledges the tick it was told about, so anything appended *after* that — settlement runs several D1 round-trips **per winner** and appends `killSettled` to the tick `bossDefeated` already went out on — is filtered by `> since` forever. That is the bug that ate the loot modal in group fights; never publish a tick mid-settlement. A `poll` returns the state plus every event after the caller's `sinceTick`, projected for that caller (`projectEventsForMember` strips the other winners' drop lists off a `killSettled`, as `projectStateForMember` strips their packs) — don't go back to per-request events, that is what left members seeing ~1 tick in 8.
- **Kill settlement is exactly-once and runs after the tick commits.** `coop_kill_settlements(session_id, kill_seq)` is the idempotency key and it lives in D1, not the room: a DO can be evicted mid-grant and replay. Never settle before the state it settles is durable, and seed `killSeq` from the ledger on reload, not from the session row.
- **A prayer's slot comes from its data, never from the caller.** `toggle_prayer` routes through `coopPrayerSlot` (`bonusType === 'protection'` → `activeProtectionPrayer`), because combat.js only mitigates from that field: taking the slot off the intent filed every protect-from-X as an offensive prayer, so it blocked nothing *and* cancelled the offensive prayer — flicking a boss in a group could not work at all.
- **The room PUSHES the beat over a WebSocket; polling is the fallback, not the plan.** `src/cloud/coopFeed.js` owns the connection and `CoopBossScreen` only receives beats — it must not learn which transport carried one. Polling cost a Worker invocation, a JWT verify and a `getOwnedCharacter` **D1 read per member per 600ms** (~800 reads/min for a full room) to deliver a fight that was always a round trip stale; the socket costs one D1 read per *connection*. A browser cannot put a header on a handshake, so `POST /api/coop/session/:id/socket` mints a **60s `coop_socket` ticket** (bound to character AND session) and the `GET` on the same path verifies it *at the edge* before proxying the upgrade to the room — an unauthenticated socket must never reach a DO. Frames are **deltas** against the projection each socket was last sent (`src/engine/coopSocketProtocol.js`, per SOCKET not per member — a reconnect can double up), and a beat where only the tick counter moved with no events is **not sent at all**, which is what makes sitting in a raid lobby free. Two rules carry over unchanged: a tick is pushed only from `tickInner`'s `finally` (never mid-settlement, §20's `publishedTick` rule), and `validateCoopAction` now lives in `functions/_lib/game/coopIntent.js` because a socket frame **never passes the edge** — leaving it there let chat through unsanitised and `toggle_prayer` through without its data-derived slot. The fallback survives on purpose — a network that blocks WebSockets answers non-101 → the client polls, paced by `nextPollDelayMs`/`src/utils/coopPolling.js` against the room's `next_tick_in_ms` (a flat 600ms wait drifts a round trip out of phase and arrives in clumps). A tap is still echoed locally until the room answers (`coopIntentEcho` — the toggles only, mirroring `applyCoopIntent`; the screen drops the echo at the tick the intent was stamped for, so a refusal simply un-does it).
- **A closed socket is weak evidence of absence, and being let go is never a dead end.** Losing the last socket back-dates that member's `lastSeen` by `COOP_SOCKET_LINGER_MS` so the ordinary staleness path ejects and writes them back — back-dating rather than a second timer, so any later poll or reconnect undoes it for free. The constant is **45s and must not be shortened back**: it was 10s, tuned only for the player who has GONE (the save lock follows the member, §20), and a phone closes sockets for a locked screen, an app switch or a wifi handover — a *suspended tab runs no timers*, so it cannot reconnect until the player looks at it. At 10s a glance at a notification cost the fight. Because a member can always be let go, the client treats `not_a_member`/`ejected`/`session_ended` as **rejoinable, not fatal** (`isRejoinableCoopCloseReason` → `coopFeed`'s `onLost` → `rejoinCoopFight`): pull the save the room wrote on the way out, then rejoin — the **same party** for a raid (joining one without a `sessionId` opens a NEW party, §21, stranding the returner alone in a lobby), any room for a boss. A boss rejoin usually returns the SAME `sessionId`, so `CombatScreen` remounts the screen off an attempt counter, never off the id. Checkpoint cadence: **15s in a fight, 60s in a lobby** (nothing is at risk in a lobby; membership/phase/readiness still force one immediately), heartbeat rows refreshed per member every **30s** against a 90s lock TTL, and both folded into **one `DB.batch`**. Do **not** lengthen the 15s fight checkpoint to save rows — its cost is a player's lost progress when a DO is evicted mid-fight.
- **Client settings edited mid-fight ride the member, not `/api/save`.** The co-op lock refuses this character's own save push and `sync.js` *drops* it, and the client pulls on exit — so anything the player changes during a fight is lost unless the room carries it. `quickPrayers` works this way (seeded in `createCoopMember`, edited by the `set_quick_prayers` intent, written back by `applyQuickPrayersToSave`); an absent field means a pre-feature session and must leave the save's value alone rather than writing an empty one. Any future in-fight setting needs the same three pieces.
- **Nothing may write the save while a room owns it.** The member's save revision is stamped at join and re-checked on every write-back (`isMemberSaveOwned`); a mismatch **refuses the write entirely** — replaying the snapshot duplicates items, writing XP alone refunds the supplies. Prevention is `assertNotInCoopSession`, which every save-writing endpoint calls (`/api/save`, `purchase`, `trading-post/**`, `actions/**`, `skip-hour`, world entry). Add it to any new one.
- **Combat mirrors the open world** (`world/server/combat.ts`): each member runs their own `processCombatTick` session against the shared boss HP, so authored boss mechanics keep working. Two invariants — only the **target** member's session resolves a boss swing (otherwise the boss attacks once per member), and only the target advances the **add's** spawn countdown (otherwise N members each spawn one).
- **Loot goes to everyone who earned it**, not one winner: every member whose own damage reached **10% of the boss's max HP** (`COOP_LOOT_DAMAGE_SHARE` / `lootEligibleCharacterIds` in `src/engine/coopBossEngine.js`; ceil, so the floor is 1 and a 0-damage member never qualifies) rolls the drop table **independently** and is granted server-side with the same collection-log/kill-count/audit side-effects as `/api/actions/monster/complete`. Attribution is the boss's HP delta across a member's tick, so every damage source counts; damage resets per boss instance on respawn, and the gate is damage-only (a member who qualified and then died is still paid). The cap of 8 means the top contributor always clears 12.5%, so a kill can never come out dry for everybody. Idempotency is therefore per CHARACTER — `coop_kill_settlements` is keyed `(session_id, kill_seq, character_id)` (migration 0032) — and the per-member settlements are independent, so one diverged save never costs the other winners their drop. A skip cannot be used to jump the threshold: `/api/skip-hour` refuses while a room owns the character.
- **Chat and purple-drop announcements are instance-wide broadcasts, and both ride the room's event ring.** Chat arrives as a `chat` intent (sanitised at the edge *and* in the room by `sanitizeChat`, `src/engine/playerChat.js`), takes **no** combat action slot and works while dead or mid-respawn, and is rate-capped per member (`chatRateVerdict`). It is queued in `pendingChat` and published on the **next** tick, never appended to the current one — an event added to a tick a client already acknowledged is filtered by `> since` forever, the same rule that keeps settlement off its own tick. Every message writes an audit row (`coop_chat`; the world writes `world_chat`) with `swallow: true` — a safety history, and an audit outage must not silence the room. The **purple-drop** announcement (`epicDrop`, `coopEpicDropEvents` in `src/engine/lootBroadcast.js`) fires for every winner whose grant contains an item past the loot modal's purple threshold (`isLegendaryItem`, unit value ≥ 1m — keep the two predicates the same, or the room celebrates something the winner does not). It carries that item only and is deliberately **not** stripped by `projectEventsForMember`: who pulled a legendary is public, the rest of their drops are not. The open world runs the same announcement through `dropBroadcastsFrom` (`world/server/bossKills.ts`), where it is **not** a boss privilege — value is the reason to shout — and a boss unique that is also legendary announces once, as epic.
- **Instances are sharded**, capped at `COOP_MAX_MEMBERS` (8): joining picks the fullest non-full session, else opens a new one — never one global boss per boss id.
- **The save lock follows the MEMBER, not the room** (`coop_session_members.last_seen_at`, 90s TTL; `characters.active_coop_session_id`; same lock class as the world session). A room stays alive while anyone is in it, so a session-wide clock left a crashed player locked out of their own save for as long as the others kept fighting. The room ejects its own stale members and **writes them back before releasing** — as does the crash sweep, so a dropped connection costs the fight, never the XP. The client must pull the save on exit, never push its own — so a push refused by the co-op lock **drops** its snapshot (`sync.js`) instead of queuing it the way the world lock's push does, or the pre-fight state lands on top of the room's write-back the moment the lock lifts. Joining WRITES the save (the snapshot), so `/api/coop/join` returns `save_revision` (on its error path too) and `cloud/coop.js` re-anchors from it; the pre-join flush treats `CHARACTER_IN_COOP_SESSION` as "a room already owns me", not a failed save, and joins anyway — refusing wedges the player behind the one call that releases the lock.
- **Boss entry gates are enforced server-side** (`coopBossRequirementFailure` → `checkBossRequirementsPure`): Slayer level and kill-count prerequisites, not just the quest. The server grants this boss's drop table, so a client-only gate is no gate.

## 21) Raid Parties (`/api/coop/raid/**`)
A raid run as a co-op session (§20 is the substrate — same room, same tick, same save lock, same 10% loot gate). Only what differs from a boss room is below.
- **A raid has a lobby; a boss room does not.** `phase` on the session state is `'lobby' | 'active'`; members may be added **only in lobby** and the gate is enforced in the ROOM (`CoopBossRoom.handleJoin`), not just the join path — the D1 row is a checkpoint behind, so it cannot be the authority on whether the host has set off. `phase` changes force an immediate checkpoint, or the lobby list keeps offering a run for seconds after nobody can enter it.
- **The host starts it.** `hostCharacterId` (the opener); `start_raid` is an ordinary intent so it orders with the tick loop — no extra endpoint. `removeCoopMember` promotes the earliest-joined member when the host leaves (`nextHostCharacterId`), or a party is stranded with a Start button nobody can press. The lobby is prep time exactly as the respawn wait is: intents apply, `tickIdleCooldowns` walks cooldowns down, nothing fights.
- **No auto-pick.** `POST /api/coop/raid/join` with no `sessionId` means **open a party**; with one it means **join that party**. Deliberately unlike the boss join, which picks the fullest room — which party you raid with is the player's call, so a full/started party is an honest refusal (`RAID_ALREADY_STARTED`, `COOP_SESSION_UNAVAILABLE`), never a reroute.
- **A raid pays once, at the end, from its own table.** Intermediate bosses emit `raidBossDefeated` and return **no kill record** — mirroring solo (`combat.js` rolls loot on `raidComplete` only). The final boss's kill record carries `sourceType: 'raids'`, and `killRewardSource` routes settlement to `rollRaidRewardsById` with collection-log and `kill_counts` filed under `raids`/`raidId`. Slayer credit lands on the final boss only, mirroring solo's `fromRaidCompletion` gate.
- **The loot gate measures the WHOLE run.** `coopLootBasisHP` returns `raid.maxHP` (every boss's HP summed at raid creation, `raidTotalHitpoints`) and member damage is **never reset between bosses** — reset it and a member who carried five bosses goes dry on the sixth. The sum counts **health the party actually removes, not health bars**: a phased boss adds every phase (Verzik 2000+3250+2500) and a `requiresDoubleKill` boss counts twice (Olm 800×2). That second bar only exists because `doubleKillCount` lives on the **shared boss record** (`state.boss`), not the member — member combat sessions are rebuilt from scratch each tick, so a per-member count regenerates the boss forever and the raid can never be finished.
- **Finishing or wiping returns the party to its lobby** (`returnPartyToLobby`) so the host can start again without regrouping; eligibility is read before the reset clears the damage it is measured from. That happens on the **same tick** the settlement publishes `killSettled`, so `CoopBossScreen` builds its loot modal **before** the lobby early-return and renders it from both branches — a modal rendered only by the fight view is set into state and never seen, which is exactly how a cleared raid paid out silently. **Dead members are not revived** — death must cost what it costs solo, and reviving also hides the death from the client, which is what reverts one-life mode.
- **The party sets off together: readiness GATES the start.** `set_ready` (lobby-only, silent outside one) sets `member.ready`, projected by `lobbyMember`; `raidPartyReady` is the gate and `raidReadyCount` the same count the lobby shows — enforced on the `start_raid` intent (`party_not_ready` refusal), not by disabling the button, which is not the authority. Both read one roster (`readinessRoster`) that excludes the **host** (Start is their answer) and the **dead** (a party returns from a wipe with its casualties, they are never revived, and the intent path refuses actions from a dead member — counting them strands the party behind someone who cannot answer). Cleared by `startCoopRaid` and `returnPartyToLobby`. New intent → add its case to `validateCoopAction` (`functions/api/coop/session/[id]/intent.js`) too: that allowlist runs at the edge, and a missing case is a 400 `unknown_action` the room never sees.
- **The lobby is the one place a member's kit is public.** `projectStateForMember` swaps `publicMember` for `lobbyMember` (adds equipment/inventory/levels) **only while `phase === 'lobby'`** — sizing up the party is the point of the screen, but eight full packs per 600ms beat is payload nobody reads. `CoopRaidLobby`/`CoopRaidPartyList` are the surfaces; the fight itself is `CoopBossScreen` unchanged, with a `Boss n/N` counter.
- Migration **0034** (`raid_id`, `phase`, `host_character_id`). `boss_id` holds the raid's CURRENT boss so every §20 query still works; boss-browser queries filter `raid_id IS NULL` so a party can never surface as a boss room.
